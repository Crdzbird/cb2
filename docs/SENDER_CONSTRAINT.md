# cb2 sender-constrained tokens

Status: design draft, decided, not implemented. Nothing in this document
is normative until it moves into PROTOCOL.md with vectors and the
checker behind it. It is written in the same shape as PROTOCOL.md so
that moving it is a copy, not a rewrite. The four questions the first
draft left open are settled in section 8.

## 1. The problem

A cb2 token is a bearer token: whoever presents it is accepted. Every
measure the library has today (short exp, the implicit assertion, the
replay check, the maximum lifetime) limits what a stolen token is worth;
none makes it worthless. Tokens leak through logs, proxies, crash
reports, browser extensions and misconfigured caches, and in each of
those cases the thief has everything the verifier asks for.

A sender-constrained token is accepted only together with a proof that
the presenter holds a key the token was bound to at issuance. The token
alone is then no more useful to a thief than a public key. This is what
RFC 7800 (proof-of-possession key semantics for JWT) and RFC 9449
(DPoP) do for JWT; cb2 can do it with less, because the pieces the
proof needs already exist in the format: a signed or sealed envelope
with a footer and an implicit assertion, a key id binding, strict claims
and a validation order.

## 2. Shape of the design

Two things are added.

1. A registered claim `cnf` in the access token, set by the issuer,
   naming the key the token is bound to.
2. A proof: a small cb2 token of a new purpose, made by the client for
   each request, that authenticates under the bound key and is tied to
   the access token, the request and the moment.

The proof is verified by the resource after the access token has
authenticated and passed every existing rule, as a new last step of the
validation order. A verifier that does not check proofs must say so
explicitly; by default a token that carries `cnf` is refused without a
proof, so a token issued as constrained is never silently accepted as a
bearer token.

Two modes exist, chosen by what `cnf` holds, because cb2 has two
purposes with different properties.

| mode | access token | `cnf` holds | bound key | proof purpose |
|---|---|---|---|---|
| public | cb2.local or cb2.public | the client's `kcb2.public` key | the client's hybrid key pair | `cb2.holder-public.` |
| local | cb2.local only | a `kcb2.local` proof key | a 32-byte secret shared by issuer, client and verifier | `cb2.holder-local.` |

The proof purposes are named after holder-of-key, the term for the
property they provide: a holder proof shows that the presenter holds
the bound key. The names are unlike any other cb2 purpose or key string
so that a header, a log line or a context string is never mistaken for
one of them.

The public mode is the general one: the client holds a key pair, the
issuer learns only the public key, and the token itself carries it, so
any verifier that can authenticate the token can check proofs with
nothing else in hand. The local mode exists because a cb2.local
access token is encrypted, so the issuer can place a fresh symmetric
proof key inside it where only the verifier can read it; the client
receives the same key over the channel that delivered the token. Its
proofs are about 400 bytes and cost a few microseconds instead of a
hybrid signature, which matters for high-rate service to service calls, and it
needs no key distribution at all. It is unsafe in a public token, whose
payload is in clear, and the verifier refuses that combination.

## 3. The `cnf` claim

`cnf` is a registered claim, a string, subject to the identifier policy
of PROTOCOL.md 9.4. Its value is a kcb2 key string:

- `kcb2.public.` followed by 2646 base64url characters: the public mode.
  The client's whole hybrid public key, as PROTOCOL.md section 7 writes
  it. The token carries the key rather than its id so that a verifier
  needs no key store and trusts nothing the client presents: the key
  arrives under the issuer's tag or signature, and the issuer bound it
  only after the client proved possession (section 6). The cost is
  about 2.6 KB per access token, accepted on purpose; a cb2.public token
  already outgrows a cookie, and a cb2.local one that carries a client
  key is a service token, not a session cookie.
- `kcb2.local.` followed by 43 base64url characters: the local mode. A
  32-byte proof key, uniformly random, generated by the issuer for this
  token and this token only, never reused and never derived from the
  token key.

An issuer MUST NOT write a `kcb2.local` value into a cb2.public token. A
verifier MUST treat a `kcb2.local` value found in a cb2.public token as
`claims_malformed`. Any other value is `claims_malformed`.

The claims writer places `cnf` after `jti` in the registered order.

## 4. The proof

A proof is a token of purpose `cb2.holder-public.` or `cb2.holder-local.`,
built exactly as PROTOCOL.md sections 6 and 5 build cb2.public and
cb2.local, with the proof header in place of the token header everywhere
the header appears: in the key derivation input and the PAE of the local
construction, in the PAE and the ML-DSA context string of the public
construction, and in the text. A proof therefore never verifies as an
access token and an access token never verifies as a proof, under the
same key, for the same reason a kcb2.local-wrap string is not a
cb2.local token.

### 4.1 Inputs

- The bound key: the client's secret key (public mode) or the proof key
  from `cnf` (local mode).
- The footer: the key id binding of PROTOCOL.md section 8 for the bound
  key, `{"kid":"<id>"}`, where the id is the client key's `kcb2.pid` in
  the public mode and the proof key's `kcb2.lid` in the local mode. Both
  are the key's default id, so the existing binding applies unchanged,
  and in the public mode the verifier derives the id from the key it
  read out of `cnf`, never from anything the client sent.
- The implicit assertion: the complete text of the access token the
  proof accompanies. The verifier holds that text, so nothing is sent
  twice, and the proof is bound to exactly one token without carrying a
  hash of it.
- The message: a claims payload (section 4.2).

### 4.2 Proof claims

The payload is a claims object under the rules of PROTOCOL.md 9.1 and
9.2 with these members, all required unless stated:

| claim | meaning |
|---|---|
| jti | a fresh id, unique per proof, for the proof replay check |
| iat | when the proof was made |
| exp | when it stops being valid; at most the verifier's proof lifetime after iat |
| htm | the HTTP method of the request, uppercase, as a custom claim |
| htu | the request target after the normalisation of 4.4, as a custom claim |
| nonce | optional: a value the verifier handed out, when it uses server nonces |

`htm` and `htu` are the names RFC 9449 uses, kept so that their
semantics need no new definition. A verifier that is not an HTTP
resource defines what `htm` and `htu` mean for it, and says so; the
claims are still required, because a proof with no statement of what it
is for can be replayed against anything.

An issuer-side proof (section 6) uses `htu` of the token endpoint and
carries no implicit assertion, since no access token exists yet.

### 4.3 Sizes and cost

| | public mode | local mode |
|---|---|---|
| proof text, typical claims | about 4.8 KB | about 400 bytes |
| client key the verifier needs | none beyond the token: `cnf` carries it, about 2.6 KB of the access token | none beyond the token |
| verifier cost per proof | one Ed25519 and one ML-DSA-65 verification, about 120 us on the reference machine | one keyed BLAKE3 derivation and one tag, about 2 us |

The public mode is the cost of a post-quantum signature per request. A
deployment that cannot afford it on a hot path and whose access tokens
are cb2.local should use the local mode; one whose access tokens are
cb2.public has no cheaper option that keeps the post-quantum property.

### 4.4 Target normalisation

Both ends normalise `htu` the same way before writing or comparing it,
so that two implementations agree on the one claim an attacker probes.
The rule is RFC 9449 section 4.3 made explicit: the target is the
request URI with the query and the fragment removed, the scheme and the
host lowercased, a port that is the scheme's default removed, and
nothing else changed; the path is kept exactly as sent, percent-encoding
included. The result is compared byte for byte in constant time. The
rule is in the protocol rather than left to each verifier so that it is
a vector in proofs.json and the checker exercises it.

## 5. Verification

The proof check is step 5 of the validation order in PROTOCOL.md 9.6,
after step 4 and before the claims are released. The verifier's rules
gain:

| rule | default | meaning |
|---|---|---|
| proof | none | the proof text presented with the request, with the request's method, target and server nonce |
| proof lifetime | 60 seconds | the most `exp - iat` a proof may claim, and the most `exp` may lie after now |
| proof replay check | required when a proof is checked | receives the proof's `jti`; refuses one it has seen within the proof lifetime |
| require sender constraint | false | a token without `cnf` is refused |
| ignore sender constraint | false | `cnf` is not checked and no proof is needed; must be said explicitly |

Step 5, stopping at the first failure:

1. If the rules ignore sender constraint, skip to release. Otherwise
   `cnf` absent: `missing_cnf` when required, else release as a bearer
   token. `cnf` present and no proof supplied: `missing_proof`.
2. Classify `cnf`. A `kcb2.local` value in a cb2.public access token is
   `claims_malformed`. In the local mode, import the proof key with the
   weak-key check; a key that fails is `claims_malformed`. In the public
   mode, import the `kcb2.public` key; a string of the wrong length or
   encoding is `claims_malformed`. Nothing the client sent is consulted.
3. Verify the proof as a `cb2.holder-public.` or `cb2.holder-local.` token
   under the bound key, with the footer rebuilt from the key's default
   id and the implicit assertion set to the access token text. The proof
   is bounded by the same size limit as the access token first. Any
   failure that depends on the proof's bytes is `proof_invalid`, one
   verdict.
4. Parse the proof claims under 9.2 and 9.4; failure is
   `proof_malformed`. Then, with t = now and s = the clock skew:
   - `jti`, `iat`, `exp`, `htm` or `htu` absent: `proof_malformed`
   - `exp <= t - s`: `proof_expired`
   - `iat > t + s`, or `exp - iat` above the proof lifetime, or `exp`
     above `t + lifetime`: `proof_expired`
   - `htm` or `htu` different from the request's, or `nonce` absent or
     different when the verifier uses nonces, compared in constant time:
     `proof_mismatch`
   - the proof replay check refuses `jti`: `proof_replayed`
5. Release the claims.

The verdicts after step 3 are detailed because the proof has
authenticated by then, exactly as the claims verdicts are detailed after
the access token has authenticated. Everything before that is one
verdict.

A verifier MUST NOT accept a proof whose implicit assertion is anything
but the access token it arrived with, MUST NOT accept a proof under a key
other than the one `cnf` names, and MUST NOT skip the replay check: the
proof lifetime is the only thing that bounds the replay store, and
without the store a captured request can be replayed for that long.

## 6. Issuance

How the bound key reaches the issuer is outside the token format, as
key distribution is for the rest of cb2, but the shape is fixed so that
the two modes compose.

Public mode. The client generates a cb2 key pair and sends its
`kcb2.public` string with the token request, together with a proof of
purpose `cb2.holder-public.` over that request: `htm` and `htu` of the
token endpoint, a fresh `jti`, no implicit assertion. The issuer verifies
the proof under the presented key, so it binds only a key the client
demonstrably holds, and writes the whole `kcb2.public` string into
`cnf`. Nothing is stored and nothing is fetched later: every verifier
reads the key out of the token it has just authenticated.

Local mode. The issuer generates the 32-byte proof key, writes its
`kcb2.local` string into `cnf` of a cb2.local access token, and returns
the same string to the client in the response that carries the token,
over the channel that already protects the token. The client keeps it as
it keeps the token. There is nothing to distribute: every verifier that
can open the token can read the proof key.

In both modes a new token means a new binding; a proof key is never
carried over, so rotation is the token lifetime.

## 7. What it defends and what it does not

Defended: a token read from a log, a proxy, a cache, a crash dump, a
screenshot or a network capture is useless without the bound key. A
captured request, proof included, can be replayed only against the same
method and target, with the same token, within the proof lifetime, and
only once past the replay check.

Not defended: a client whose bound key is stolen along with the token,
which is the case for malware on the client; a verifier that is
compromised; a browser client whose key is extractable, which today
means every post-quantum key, since WebCrypto has no ML-DSA and a
JavaScript implementation keeps the key in script memory. For a browser
client the local mode is the realistic one, and it protects against
leakage of the token through channels that do not also leak the key,
which is most of them.

The implicit assertion makes the proof worthless with any other token.
The proof header, used as the ML-DSA context string and in the local
key derivation, makes a proof worthless as anything but a proof, and a
signature the client made for any other purpose worthless as a proof.
The footer binding means a proof made under any key but the one in
`cnf` fails closed.

## 8. Decisions

The first draft left four questions open; they were settled with the
owner on 2026-11-04.

1. Names: `cb2.holder-public.` and `cb2.holder-local.`, after
   holder-of-key, chosen for being unlike any other cb2 purpose or key
   string. The generic `proof` and the RFC 7800 `pop` were rejected as
   too easy to confuse with other things called proofs.
2. The local mode stays, and is implemented after the public mode. The
   objection that three parties hold a secret is already true of every
   cb2.local deployment, where issuer and verifier share the token key;
   the proof key adds a secret worth one token for one lifetime, and in
   return the mode is the only one a browser can hold safely today and
   the only one cheap enough for a hot path.
3. `cnf` carries the whole public key, not its id. The owner asked for
   the safest option regardless of length: a verifier then needs no key
   store and trusts nothing presented by the client, since the key
   arrives under the issuer's own tag or signature.
4. Target normalisation is in the protocol, as RFC 9449 defines it, so
   that it is testable by vectors (section 4.4).

## 9. Implementation plan

In the order the pieces depend on each other.

1. `detail::PublicCore` parameterised by header, as `LocalCore` already
   is, so that `cb2.holder-public.` reuses the signing and verification
   code byte for byte; `Local` already supports a header parameter
   through the core.
2. A `Proof` class with `make_public`, `make_local`, `verify_public`,
   `open_local`, taking the bound key, the proof claims, the access
   token text and the request binding.
3. `cnf` as a registered claim in `Claims`, written after `jti`, parsed
   and checked as section 3 says, and the `htu` normalisation of 4.4 as
   a function both the proof maker and the verifier call.
4. The rules and verdicts of section 5 in `ValidationRules`, `Error` and
   `error_name`, with the proof check as step 5 of `Token::open` and
   `Token::verify`.
5. Tests for every verdict, vectors in a new `proofs.json` with both
   modes and their failure cases, the playground commands `proof` and
   `check ... proof=`, the web scenario, the section in PROTOCOL.md with
   the vector file format and a worked example, and the checker extended
   to the new purposes.
6. SECURITY.md: the claim, its assumptions and what is not claimed, as
   section 7 here.

Nothing in the existing format changes; a verifier that never sets a
proof rule and never sees a `cnf` claim behaves exactly as today.
