# Cut cb2 tokens by encoding, not compression

cb2.local can shrink from 470 to about 262 characters, a 44 percent cut, with every security parameter kept exactly as it is today: the 32-byte nonce, the 32-byte keyed-BLAKE3 tag and its 2^128 key commitment, Ed25519 together with ML-DSA-65 for public tokens, authentication before any parsing, and the distinct verdicts the API reports. The cut comes from the format alone. The JSON claims become a strict CBOR profile with CWT integer keys, epoch integer times and a binary jti, which takes them from 217 to 106 bytes on the local test set, and the 63-byte JSON key-id footer becomes a 16-byte binary key id that stays authenticated. An optional second step interns the issuer and audience through a table whose digest is authenticated with every token, which brings the claims to about 72 bytes and the token to about 216 characters without changing any cryptographic parameter. Compression is rejected: after the CBOR encoding it adds nothing, and on JSON its output length leaks claim values. cb2.public keeps its signatures, so encoding saves only about 4 percent (4,883 to about 4,675); the large cuts the research found for public tokens all lower security or are not ready, and this revision of the plan takes none of them (see Security floor below). The repository's own vectors show the most urgent size problem: a sender-constrained cb2.public token is 8,274 characters plus a 4,770-character proof, which exceeds the default 8 KB per-header limits of nginx and Apache; a binary cnf is the one change that helps it without touching the cryptography.

## Claims fill cb2.local, signatures fill cb2.public

The two purposes need different fixes because their bytes go to different places. Measured on 1,000 test claim sets with the library at commit 8cd81bc ([local measurements](notes-local-measurements.md)), a cb2.local token has these parts: a 10-character prefix; base64url of a 32-byte nonce, 217 bytes of claims (211 to 224) and a 32-byte tag, which comes to 375 characters; a dot; and an 84-character footer holding `{"kid":"kcb2.lid.<44 chars>"}`. That totals 470. A cb2.public token has an 11-character prefix, 4,787 characters of claims plus 3,373 bytes of signature, a dot and the same 84-character footer, for 4,883 in all. In cb2.local the claims and the footer together are about 80 percent of the text. In cb2.public the signatures alone are 92 percent. One researcher's worked baseline put the local body at 382 characters, which adds up to 477 rather than 470. The body of 281 bytes encodes to 375 characters, so this report uses the measured anatomy throughout.

Size matters because of where tokens travel. RFC 6265bis tells browsers to ignore a cookie whose name plus value exceeds 4,096 octets ([RFC 6265bis](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis)). nginx rejects a header field larger than one 8 KB buffer with a 400 ([nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html)). Apache caps a field at 8,190 bytes ([Apache](https://httpd.apache.org/docs/2.4/mod/core.html)), and gRPC suggests 8 KiB of metadata as a default limit ([gRPC](https://grpc.io/docs/guides/metadata/)). HTTP/2 header compression does not help a bearer token. nghttp2 never indexes `Authorization`, and its source says Firefox follows the same rule ([nghttp2](https://github.com/nghttp2/nghttp2/blob/master/lib/nghttp2_hd.c)). QPACK's dynamic table defaults to zero capacity ([RFC 9204](https://www.rfc-editor.org/rfc/rfc9204.html#section-5)). So the full token is sent on every request, and every character saved is saved on every call.

## Schema-aware CBOR takes the claims from 217 to 72 bytes and makes compression pointless

### CWT-style encoding is standard, deployed and enough

CWT (RFC 8392) keeps JWT's claim semantics but writes the names as small integers (iss=1, sub=2, aud=3, exp=4, nbf=5, iat=6, cti=7). Times are untagged integers, and the token id is a byte string ([RFC 8392](https://www.rfc-editor.org/rfc/rfc8392.html)). The RFC's own example claims set is 80 bytes. The IANA registry is active: it was updated in July 2026 and has assigned 8 to cnf and 9 to scope ([IANA CWT registry](https://www.iana.org/assignments/cwt/cwt.xhtml)). Capability-token formats went the same way. Biscuit uses protobuf with interned strings "to reduce size" ([Biscuit spec](https://github.com/eclipse-biscuit/biscuit/blob/main/SPECIFICATIONS.md)), and macaroons v2 moved to a varint binary layout that its designer found could be about 50 percent smaller ([libmacaroons format](https://github.com/rescrv/libmacaroons/blob/master/doc/format.txt)). The local measurements show where the cb2 bytes go:

| claims encoding (1,000 test sets) | mean bytes | range | value-dependent length |
|---|---:|---|---|
| JSON as today | 217.4 | 211 to 224 | field lengths only |
| zstd -19, no dictionary | 161 | | yes |
| zstd -19 with a 4 KB trained dictionary | 62 | 55 to 76 | yes, strongly |
| CBOR, CWT integer keys, epoch integer times | 127.4 | 121 to 134 | field lengths only |
| "tight" CBOR: plus exp as delta, 16-byte binary jti, iss and aud as table indexes | 72.0 | 70 to 73 | field lengths only |
| tight CBOR, then zstd with the dictionary | 75 | | yes |

The savings come from four places, each easy to explain. Two RFC 3339 strings take 54 JSON bytes but only 10 CBOR bytes as epoch integers. A text UUID jti takes 38 bytes, against 17 as a CBOR byte string. Each claim name shrinks from 5 or more bytes to 1. The 24-byte issuer URL and the audience shrink to small indexes. A researcher's single-example script found a slightly smaller result, 106 bytes for CWT keys with a binary jti and 49 to 59 bytes with aggressive interning. The difference comes from interning more values (role as well as iss and aud) on one payload. The measured 72 bytes over 1,000 sets is the figure to plan with. Converting times to integers loses nothing in cb2: its reader already ignores fractional seconds (docs/SPEC.md section 8.1). Writing exp as a delta from iat saves about 2 bytes but departs from CWT's NumericDate semantics, so the design below keeps exp absolute and costs about 74 bytes.

The risks are parser risks, and cb2 already has the right reflexes. A Bishop Fox study of 49 JSON parsers found risky behaviour in every language, including inconsistent handling of duplicate keys ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). CBOR brings its own version of these problems. A map with duplicate keys is well formed but not valid. Integers can be encoded in more than one length. There are two incompatible deterministic key orders, plus the float edge cases ([RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html)). COSE sidesteps canonicalisation by authenticating the exact bytes ([RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html)), and cb2 already does that. Strictness is still worth having, because cb2 has five implementations that must agree on accept or reject: C++, the Python checker, and the Java, Go, JS and Swift bindings. The profile should reject duplicate keys, non-shortest integers and lengths, indefinite lengths, tags, floats, trailing bytes and negative times. Each claim set then has exactly one encoding. One cb2-specific wrinkle needs an explicit decision: the JSON reader keeps numbers as text and never converts them, so a compact writer must refuse custom claim numbers that are not exact 64-bit integers. Silent rounding is not an option. Another trap is borrowing small integers privately. Keys 8 and 9 already mean cnf and scope in CWT. cb2 should either adopt the IANA table exactly or put application claims under text keys.

Interning the issuer and audience is the one step with a real semantic hazard. If a verifier's table is stale or different, the same integer silently means a different string. There is a cleaner option that costs no bytes. cb2's verifier rules must already name the expected issuer and audience (SPEC.md section 8.3, step 0). The compact profile can therefore leave iss and aud out of the payload and bind them the way PASETO binds implicit assertions: authenticated, but never transmitted ([PASETO rationale](https://github.com/paseto-standard/paseto-spec/blob/master/docs/Rationale-V3-V4.md)). If the elided values or an interning table are put into the authenticated input, a mismatch fails the tag instead of being misread. The cost is diagnostic. `issuer_mismatch` and `audience_mismatch` collapse into the single `invalid` verdict, and `allow_any_issuer` cannot apply to such tokens. Applying this pattern to iss and aud is this report's own design inference; no source shows a deployed format that does it.

### Compression loses to encoding and brings two vulnerability classes

JOSE allows compression only in JWE, through `"zip":"DEF"` ([RFC 7516](https://www.rfc-editor.org/rfc/rfc7516.html)). The JWT best-practice RFC later said data SHOULD NOT be compressed before encryption, because compressed length reveals content, especially when an attacker controls part of the data ([RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)). In 2024 nearly every major JOSE library shipped a decompression-bomb fix. python-jose, go-jose, jwcrypto and jose4j added caps of about 250 kB on output or token length ([python-jose PR 352](https://github.com/mpdavis/python-jose/pull/352), [go-jose CVE-2024-28180](https://advisories.gitlab.com/golang/github.com/go-jose/go-jose/v3/CVE-2024-28180/), [jwcrypto CVE-2024-28102](https://nvd.nist.gov/vuln/detail/CVE-2024-28102), [jose4j](https://bitbucket.org/b_c/jose4j/issues/220/vuln-zip-bomb-attack)). panva/jose removed compressed payloads entirely in v5 ([GHSA-hhhv-q57g-882q](https://github.com/advisories/GHSA-hhhv-q57g-882q)). The length oracle is the more serious problem for cb2.local. BREACH and HEIST showed that attacker-influenced input, compressed next to a secret, can leak the secret through repeated length observations. HEIST could do it from browser JavaScript with no network position ([BREACH](https://css.csail.mit.edu/6.566/2014/readings/breach.pdf), [HEIST](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows.pdf)). A token with an attacker-chosen display name next to a secret role or tenant, re-issued on demand, meets all of those conditions. The measured 55 to 76 byte spread of dictionary output is exactly that signal. A trained dictionary makes it sharper, because a correct guess compresses to a dictionary reference.

The precedents keep compression only behind padding or signatures. Rack's encrypted cookies pair optional deflate with padding to a multiple of 32 bytes ([Rack encryptor](https://github.com/rack/rack-session/blob/main/lib/rack/session/encryptor.rb)). Django compresses only signed, unencrypted values, and checks the signature before inflating ([Django signing](https://github.com/django/django/blob/4.2.4/django/core/signing.py)). PADME padding leaks only O(log log M) bits, but across 55 to 76 bytes it still produces five buckets, about 2.3 bits per token, which is enough for an adaptive attacker to confirm guesses ([PADME](https://arxiv.org/pdf/1806.03160)). The fix that is actually safe is a single fixed size of about 80 bytes. That is already larger than the 72 to 74 bytes tight CBOR gives with no compressor, no dictionary to ship to five bindings, and no new parser. For cb2.public the confidentiality concern disappears, since signed claims are readable anyway, but the gain also disappears: claims are about 2 percent of a compact public token. The verdict is to reject compression for both purposes. The decision rests on the measurements more than on caution: the schema already does the compressor's job, and does it with a length that depends only on field lengths, which today's JSON also leaks.

## The key-id footer is the largest fixed cost, and the tag stays at 32 bytes

Every envelope parameter was costed against the security margin it gives up. Character savings below are for base64url and are cumulative in the order shown, from the local measurements and the researchers' layout arithmetic.

| parameter | change | saves | what it costs | precedent | verdict |
|---|---|---:|---|---|---|
| key id | 63-byte JSON footer to a 9-byte binary id | about 72 chars | collisions cost an extra trial verification, never acceptance, because the id stays authenticated | Tink 4-byte id, Biscuit uint32 | adopt |
| nonce | 32 to 24 bytes | 11 chars | collision chance 2^-97 at 2^48 tokens per key | Branca, libsodium, XChaCha20 | adopt |
| nonce | 32 to 16 bytes | about 21 chars | safe only up to about 2^48 tokens per key at 2^-32 | none for KDF salts | reject |
| tag | 32 to 16 bytes | about 21 chars | key commitment falls from 2^128 to 2^64 | Branca and Poly1305 (16) | reject |
| alphabet | base64url to Z85 or base91 | 6.25 percent on HTTP/1.1 | not token68-legal, and larger on HTTP/2 | none for bearer tokens | reject |
| prefix | `cb2.local.` to 3 or 4 chars | 6 to 7 chars | less readable for humans and secret scanners | GitHub `ghp_`, Branca 0xBA | owner's call |

**The key id.** PASERK's 33-byte lid is a collision-resistant fingerprint, sized so that it base64url-encodes to 44 characters without padding ([PASERK ID](https://github.com/paseto-standard/paserk/blob/master/operations/ID.md)). A token only needs to select a key. Tink prefixes ciphertexts with 1 version byte and a 4-byte key id, treats that id as an unauthenticated hint, and falls back to trying keys ([Tink wire format](https://developers.google.com/tink/wire-format)). COSE says applications must not assume kid values are unique ([RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html)). cb2 binds the footer under the tag or signature, so a short id that collides can only cause a failed verification. The issuer can also refuse to create a key whose short id collides with a live key. An 8-byte prefix of the existing kcb2.lid, with the full lid kept in the key store, keeps key management unchanged and cuts the token's key-id cost from 85 characters to about 13.

**The nonce.** cb2 derives Ek, n2 and Ak from K and the nonce through keyed BLAKE3, so the only requirement on the nonce is that it does not repeat. PASETO's 32 bytes come from using the whole random value as a KDF input and give it a stated budget of 2^112 tokens per key. The PASETO documents give no birthday-bound reason beyond that ([PASETO rationale](https://github.com/paseto-standard/paseto-spec/blob/master/docs/Rationale-V3-V4.md)). With 24 bytes, a random nonce reaches a 50 percent collision chance only after about 2^96 messages ([XChaCha draft](https://datatracker.ietf.org/doc/html/draft-arciszewski-xchacha-03)), and Branca uses exactly that length ([Branca](https://github.com/tuupola/branca-spec)). In cb2 a repeated nonce would reuse the keystream but not enable forgery, because the BLAKE3 tag is a PRF rather than a one-time MAC. The failure mode is milder than Poly1305's.

**The tag.** Truncation is where the security cost is real. A 128-bit PRF tag is far beyond online forgery reach: NIST's formula 2^-(lambda - t) gives 2^-88 even after 2^40 rejected attempts ([SP 800-107r1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-107r1.pdf)). Key commitment is different. It is an offline birthday search, and Bellare, Hoang and Wu argue that standards should target 128-bit commitment, which needs about 256 bits of expansion ([committing AE landscape](https://csrc.nist.gov/csrc/media/Events/2023/third-workshop-on-block-cipher-modes-of-operation/documents/accepted-papers/The%20Landscape%20of%20Committing%20Authenticated%20Encryption.pdf)). cb2's SPEC section 9 documents its commitment with a 2^128 bound, and PROTOCOL section 12 forbids Poly1305 for this reason. Saving 21 characters would break a published claim. Truncation would also create a cross-length hazard: shorter BLAKE3 outputs are prefixes of longer ones ([BLAKE3 spec](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.pdf)).

**The text encoding.** base64url is already the best choice. RFC 9110's token68 admits only the base64url alphabet plus a few characters ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-11.2)). Under the HPACK and QPACK Huffman code ([RFC 7541](https://www.rfc-editor.org/rfc/rfc7541.html)), base64url costs about 1.065 wire bits per payload bit, against 1.166 for Z85 and 1.182 for base91, because their punctuation gets long codes. That figure is the researcher's own computation from the RFC table.

Applied in sequence, the local ladder runs as follows. Today's token is 470 characters. The short key id brings it to 398, and the 24-byte nonce to 387. Moving to CBOR without interning gives about 237; that figure is an estimate built from about 104 bytes of claims and has not been measured. Tight CBOR with the 32-byte nonce is 205, measured, and with the 24-byte nonce it is 194, measured. For comparison, a Branca token carrying the same JSON claims is about 350 characters and has no key id or key commitment.

## Only the signature moves cb2.public, and today only ML-DSA-44 is ready

The measured options below use liboqs 0.16.0 on an M3 Max with a 217-byte message, plus libsodium Ed25519 for the classical half. Token sizes assume compact claims and a short key id. The researchers' projections were 300 to 400 characters larger because they kept JSON claims and the long footer. They also quoted ML-DSA-65 signing at about 150 us. The local measurement, used here, is 120 us.

| PQ half (with Ed25519) | sig B | pk B | sign / verify us | token chars | status, Nov 2026 |
|---|---:|---:|---|---:|---|
| ML-DSA-65 (today) | 3,309 | 1,952 | 120 / 64 | 4,618 | FIPS 204, RFC 9964, RFC 10073 |
| ML-DSA-44 | 2,420 | 1,312 | 86 / 38 | 3,432 | FIPS 204, RFC 9964, RFC 10073 |
| Falcon-padded-512 | 666 | 897 | 182 / 31 | 1,094 | FIPS 206 not published |
| MAYO-2 | 186 | 4,912 | 143 / 38 | 454 | NIST round 3; attacked |
| UOV OV-Is | 96 | 412,160 | 40 / 19 | 334 | NIST round 3; reparameterising |
| Merkle batch 2^10, ML-DSA-65 root | n/a | n/a | amortised | 563 | design only for tokens |
| Merkle batch 2^16 | n/a | n/a | amortised | 819 | design only for tokens |

**ML-DSA-44 is the only cut available now.** The sizes come from the liboqs datasheet ([liboqs ML-DSA](https://raw.githubusercontent.com/open-quantum-safe/liboqs/main/docs/algorithms/sig/ml_dsa.yml)). JOSE and COSE register all three ML-DSA levels without preferring one ([RFC 9964](https://www.rfc-editor.org/info/rfc9964)). The LAMPS composite RFC 10073 defines both cb2's current pair, id-MLDSA65-Ed25519-SHA512, and id-MLDSA44-Ed25519-SHA512 ([LAMPS composite](https://datatracker.ietf.org/doc/draft-ietf-lamps-pq-composite-sigs/)). The pair cuts the token by 30 percent, brings it under the 4,096-octet cookie limit, and nearly halves verify time. The obstacle is policy, not cryptanalysis. BSI's TR-02102-1 (2026-01) reportedly marks ML-DSA-44 as not recommended and wants PQ signatures combined with a classical one ([postquantum.com on BSI](https://postquantum.com/security-pqc/bsi-tr-02102-cryptographic-guideline-update/)). CNSA 2.0 allows only ML-DSA-87 ([postquantum.com on CNSA 2.0](https://postquantum.com/cnsa-2-0/global-pqc-requirements/)). Both of those come through secondary sources, and ANSSI's position on level 2 is still unresolved. For tokens that live a few minutes, a forgery is useful only before expiry, so category 2 is technically defensible. It must be a separate header, however. Folding it into cb2.public would introduce the in-token algorithm agility that PROTOCOL section 11 forbids. Dropping Ed25519 would save only 85 characters and give up the hedge BSI asks for, even though NIST IR 8547 deprecates EdDSA after 2030 ([Quantum Computing Report on IR 8547](https://quantumcomputingreport.com/nist-releases-final-ir-8547-establishing-definitive-post-quantum-cryptography-transition-timeline-and-deprecation-schedules/)). Keep the hybrid.

**Defer FN-DSA and reject the on-ramp schemes for now.** NIST sent the FIPS 206 draft for approval in August 2025, and as of November 2026 no public draft exists ([DigiCert](https://www.digicert.com/blog/quantum-ready-fndsa-nears-draft-approval-from-nist)). Cloudflare points out that Falcon signing needs floating point that is hard to make constant time. It also notes that Falcon has no middle security level: Falcon-512 is category 1 and Falcon-1024 roughly doubles the size ([Cloudflare](https://blog.cloudflare.com/another-look-at-pq-signatures/)). FIPS 204 changed details relative to Dilithium, so a wire format built on round-3 Falcon could need to change once FIPS 206 lands. NIST advanced nine schemes to round 3 in May 2026, and HAWK was then withdrawn ([NIST round 3](https://csrc.nist.gov/projects/pqc-dig-sig/round-3-additional-signatures)). IR 8610 records a wedge attack that left MAYO-2 about 30 bits short of its target, follow-up attacks that put some UOV sets below target, and a SNOVA that NIST does not consider stable. It also expects round 3 to take about two years ([NIST IR 8610](https://nvlpubs.nist.gov/nistpubs/ir/2026/NIST.IR.8610.pdf)). SLH-DSA is larger than today's signature (7,856 bytes at its smallest), and stateful LMS cannot safely share state across a horizontally scaled issuer. Neither shrinks anything.

**Amortisation is the long-term lever, but tokens are not ready for it.** Merkle Tree Certificates (IETF PLANTS, revision -08) sign subtree heads once. Each certificate then carries only an inclusion proof of at most ceil(log2 n) 32-byte hashes, and relying parties pre-load "landmark" subtrees. The draft estimates 736 bytes and no signatures at about 5.4 million certificates per landmark ([MTC draft](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)). Chrome and Cloudflare's 2026 experiment found landmark handshakes about 9 percent faster at the median. Most clients picked up a new landmark within 2 to 3 hours ([IETF 125 results](https://datatracker.ietf.org/meeting/125/materials/slides-125-plants-mtc-experiment-early-results-01)). A delay of hours is exactly the problem for 15-minute access tokens. A landmark-relative token cannot be used until its root has been signed and fetched. The saving also exists only when the root signature stays out of the token: a self-contained batched token would be larger than today's. Batching on its own amortises signing CPU, not size. SandboxAQ measured under 100 extra bytes per signature with up to 467 percent more throughput ([SandboxAQ](https://cryptographycaffe.sandboxaq.com/posts/batch-signing/)). The 2020 TLS batch-signing draft warns that signatures under one root are linkable and reveal the batch size ([TLS batch signing](https://datatracker.ietf.org/doc/html/draft-ietf-tls-batch-signing)). No token system ships this pattern today. It belongs in a research phase, where it would also give issuance transparency.

**Two shortcuts break the reason cb2.public exists.** A delegated Ed25519 key, in the style of RFC 9345 delegated credentials ([RFC 9345](https://www.rfc-editor.org/rfc/rfc9345.html)), shrinks per-token signatures to 64 bytes. But each token would then be only classically authentic, and quantum forgery is the threat SPEC section 9 says the hybrid closes. KEM-based authentication, as in AuthKEM ([AuthKEM draft](https://datatracker.ietf.org/doc/html/draft-celi-wiggers-tls-authkem-07)), authenticates only to a designated verifier. Once it is amortised, it is the same thing as a cb2.local token keyed through kcb2.seal. That is a legitimate pattern. When the verifier set is known and verifiers may hold a key that can mint tokens, cb2 should document "seal a local key to each verifier" as the 194-character, fully post-quantum answer. Lattice signature aggregation produces proofs of tens of kilobytes ([ethresear.ch](https://ethresear.ch/t/lattice-based-signature-aggregation/22282)) and helps only a verifier checking many signatures at once. cb2 verifiers check one token at a time.

## Reference handles fix header limits, and bound public tokens need them most

A random 32-byte handle with a short prefix is about 51 characters. Everything else moves server-side, and the standards for that already exist: RFC 7662 introspection requires the endpoint to authenticate callers and limits caching to `exp` ([RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html)). Curity's phantom-token pattern swaps the handle for the full token at a gateway. Its NGINX module and Kong plugin cache the result, with an example TTL of 900 seconds ([Curity phantom token](https://curity.io/resources/learn/phantom-token-pattern/), [Kong plugin](https://github.com/curityio/kong-phantom-token-plugin)). Curity's split-token variant, which gives the client only the signature, inverts badly for cb2.public, because the ML-DSA signature is most of the token ([Curity split token](https://curity.io/resources/learn/split-token-pattern/)). For storage, the Paragon split-token design is a good template: store only a hash of the handle and compare in constant time ([Paragon](https://paragonie.com/blog/2017/02/split-tokens-token-based-authentication-protocols-without-side-channels)). GitHub's prefixes with a CRC32 checksum show how a handle stays scannable ([GitHub token formats](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)). Adoption runs in both directions, though. In October 2026 GitHub completed a move of its App installation tokens from a 40-character stateful handle to a stateless token of about 520 characters, accepting a 13-fold size increase to get rid of the lookup ([GitHub changelog](https://github.blog/changelog/2026-10-02-stateless-github-app-installation-tokens-rolled-out/)). Reference handles are a deployment option with a hard runtime dependency, not a better token format. cb2 should document the pattern and perhaps ship a small handle helper, not a new purpose.

The repository's own vectors show where that option is most needed. In tests/vectors/proofs.json, a sender-constrained cb2.public access token is 8,274 characters. Its `cnf` carries the client's 2,658-character kcb2.public string inside JSON, which is then base64url-encoded a second time. The `cb2.holder-public.` proof that accompanies it adds another 4,770 characters. As one `Authorization` field, the access token alone is larger than nginx's 8 KB buffer and Apache's 8,190-byte field limit, and the pair is well past gRPC's 8 KiB metadata guideline. The compact format removes one layer of that double encoding by carrying `cnf` as a binary key, which saves about 900 characters (an estimate). An ML-DSA-44 client key saves more. Below that, the remaining choices are binding the client key by its kcb2.pid with verifier-side key registration, which reverses a decision SPEC section 8.5 made on purpose, or putting a reference handle in front. RFC 9449 handles the same problem by binding with a key thumbprint (`jkt`) ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)).

## Security floor

This plan was revised so that no step lowers security. The analysis sections above describe every option the research found, including ones that trade security for size; the plan below takes only the ones that keep every documented property. These are fixed for every new header and cannot be traded for characters:

- the nonce stays 32 random bytes, fed whole into the key derivation as in cb2.local today;
- the tag stays a 32-byte keyed-BLAKE3 output, keeping the 2^128 key-commitment bound in SPEC.md;
- cb2.public keeps Ed25519 and ML-DSA-65 (NIST category 3), both required, with the same FIPS 204 context discipline;
- the token is authenticated before a single byte of the claims is parsed, and the length limit is applied before authentication;
- the key id stays inside the authenticated data, so a wrong or colliding id can only fail verification, never select a key silently;
- every verdict the API reports today (issuer_mismatch, audience_mismatch, expired and the rest) keeps its meaning;
- nothing is compressed.

The first version of this plan contained five steps that crossed that floor. They are removed or changed as follows.

| step in the first version | what it gave up | decision |
|---|---|---|
| 24-byte nonce instead of 32 | the nonce collision margin drops from the cb2.local design budget to about 2^-97 at 2^48 tokens per key; small, but a real reduction | removed; the nonce stays 32 bytes (costs 11 characters) |
| compact public header with Ed25519 and ML-DSA-44 | NIST category 3 to category 2; below what BSI recommends and what CNSA 2.0 allows | removed; cb2.public stays ML-DSA-65 |
| issuer and audience bound without being sent (old Phase 2) | issuer_mismatch and audience_mismatch collapse into invalid, allow_any_issuer stops working, and the construction is new and unreviewed | removed; replaced by a digest-bound table that still reports both verdicts |
| 8-byte key-id prefix | none cryptographically, since the id is authenticated, but a 64-bit id leaves less room against accidental collisions across large key sets | changed to 16 bytes (128 bits), which costs 11 characters |
| Merkle-batched public tokens (old Phase 4) | tokens from one batch become linkable and verifiers depend on fetching fresh signed roots; a stale root means refused tokens | kept only as research, not planned for the branch |

Still rejected, as before: compression (length side channel and decompression bombs), tag truncation (breaks the 2^128 commitment), alternative text alphabets (no gain on the wire), delegated classical keys (give up quantum unforgeability), FN-DSA until FIPS 206 is final, and the NIST on-ramp schemes, whose parameter sets are still being attacked. A reference handle is not a token format and is left to deployments.

## A three-phase plan for the compact-tokens branch

### The recommended design

PROTOCOL.md section 11 already decides the framing: any change to the encoding or layout needs a new header, never a flag inside a cb2 token. The branch defines a new header family that cb2 verifiers reject. This plan calls it cb3, with `cb3.local.` and `cb3.public.`; the names are the owner's to choose. The readable purpose word stays: it is the domain separator in the key derivation and the PAE, and secret scanners match on it.

cb3.local has this body: the 32-byte nonce, the ciphertext of the claims and the 32-byte keyed-BLAKE3 tag, with Ek, n2 and Ak derived exactly as in cb2 but under the new header. The footer is a binary 16-byte key id taken from the kcb2.lid hash, authenticated as now. The claims are a strict deterministic CBOR map: CWT keys 1 to 7, absolute epoch integer times, the jti (cti) as a byte string, application claims under text keys, no floats, no tags, no indefinite lengths, no duplicate keys, and shortest-form integers only. cb3.public uses the same claims codec and key id with exactly today's Ed25519 and ML-DSA-65 construction.

| phase | scope | target size | exit criterion |
|---|---|---:|---|
| 0 | size and speed harness on the 1,000-set corpus, in CI, with exact-length assertions | n/a | today's 470 and 4,883 reproduced by the harness |
| 1 | cb3.local and cb3.public: CBOR claims profile, 16-byte binary key id, binary cnf; nonce, tag and signatures unchanged | local about 262, public about 4,675 | all vectors pass in C++, the Python checker and every binding; differential fuzzing clean; the security floor checks pass |
| 2 | optional interning of issuer and audience through a table both sides configure, whose digest is part of the authenticated input; issuer_mismatch and audience_mismatch still reported after authentication | local about 216 | a token checked against a different table is refused; both verdicts still distinguishable |

The sender-constrained public token is the case to measure first in Phase 1, since it is the one that fails real header limits today. Its size comes from the public key carried in cnf as base64 text inside JSON; carrying it as raw bytes in CBOR saves about a quarter of that field, an estimate to confirm in Phase 0.

### Phase 0 result

Phase 0 is done on the branch: `cb2_size` (bench/bench_size.cpp) builds the 1,000-set corpus from a fixed seed, prints sizes and timings, and `cb2_size --check bench/size_expected.txt` asserts every row exactly in CI, in the release, sanitizer and no-liboqs builds. It reproduces the starting point: cb2.local 470.194 characters on average and cb2.public 4,883.194. It also measures the bound tokens the plan names as the urgent case. A cb2.public token bound to a client key pair is 8,431 to 8,448 characters, every one over the 8,192-byte nginx header default, and its holder proof is 4,819. A cb2.local token bound to the same key pair is 4,026 on average, so the client's public key in cnf alone costs about 3,560 characters. That is where Phase 1's binary cnf has the most to save.

### Phase 1 result

The core of Phase 1 is on the branch: cb3.local and cb3.public in the C++ library (include/cb2/cbor.hpp and include/cb2/compact.hpp), section 15 of PROTOCOL.md, tests/vectors/cb3.json, the cb3 checks in the C++ suite and in tools/check_vectors.py with its own CBOR reader and writer, the fuzz target fuzz_compact, and cb3 rows in cb2_size. Measured on the 1,000-set corpus, mean characters:

| token | cb2 | cb3 | change |
|---|---:|---:|---:|
| local | 470.2 | 260.2 | -44.7% |
| local bound to a local proof key | 554.2 | 308.2 | -44.4% |
| public | 4,883.2 | 4,673.2 | -4.3% |
| local bound to a client key pair | 4,026.2 | 2,912.2 | -27.7% |
| public bound to a client key pair | 8,439.2 | 7,325.2 | -13.2% |

The bound public token now fits one 8 KB header field (7,317 to 7,334 characters), the case the plan named first. Sealing is faster because there is less to encrypt and no JSON to write (cb3.local seal 3.65 us against 5.40, open 2.56 against 3.64 on the same run); signing and verifying are unchanged within noise, as the signatures dominate. Every item of the security floor holds by construction and is tested: the nonce and tag lengths, the signature pair, cross-header refusal, the key digest binding, the verdicts, and a tamper sweep of every character.

Not yet done in Phase 1: the C ABI and the seven language bindings do not expose cb3. They follow once the format is reviewed, so that a change to the format does not have to be made eight times.

### Protocol and test-vector changes

PROTOCOL.md needs a new chapter for each cb3 header. Each states the body layout by offset, the PAE, and a CBOR profile section that lists every rejection rule and its error: `invalid` before authentication and `claims_malformed` after. The validation order stays the same: length limit first, authentication second, CBOR parsing only after authentication. SECURITY.md restates that the nonce, tag and signature parameters are unchanged from cb2 and gives the key-id collision rule. MIGRATION.md says that cb2 and cb3 are separate headers and that neither verifier accepts the other's tokens. Under tests/vectors, new files cb3_local.json and cb3_public.json mirror Appendix A and record intermediate values (CBOR claims hex, key id, nonce, ek, n2, ak, PAE, tag) so a divergence can be located. A claims file holds acceptance and rejection cases for duplicate keys, non-shortest integers, indefinite lengths, tags, floats, negative times, trailing bytes, reserved integer keys and, in Phase 2, unknown table indexes and a wrong table digest. Cross-header vectors cover a cb2 token given to a cb3 verifier and the reverse. The tamper sweep covers every position of a cb3 token. tools/check_vectors.py gets its own CBOR decoder, written from the document alone, so that the independent second implementation still exists.

### How to measure success

Success means exact numbers on the same 1,000-set corpus and an unchanged security argument. The mean and maximum cb3.local length should be about 262 characters or less in Phase 1 and about 216 or less with Phase 2. cb3.public should be about 4,675 or less, and the sender-constrained public token should be measured against the 8 KB header limit. Every success vector should be reproduced byte for byte across the C++ library, the Python checker and the Java, Go, JS, Swift and Dart bindings. A differential fuzzing campaign over a shared CBOR corpus should find zero cases where two implementations disagree on accept or reject. Seal, open, sign and verify times should not regress. Each item in the security floor gets a written check in docs/VERIFICATION.md: the nonce and tag lengths, the 2^128 commitment, the unchanged public signature pair, tag-before-decrypt, length-before-parse, and that every verdict keeps its meaning.

## Conclusion

Almost all the waste in cb2.local is in the format, not the cryptography: text claim names, text dates and a JSON-wrapped key fingerprint. Removing only that waste cuts the token by 44 percent, or by about 54 percent with the optional digest-bound table, while every cryptographic parameter stays exactly as it is. For cb2.public the finding is the opposite: the size is the signatures, and every way the research found to make them smaller either lowers the security level or is not standardized yet. This plan keeps the signatures and accepts the size, and leaves Falcon and Merkle-batched roots as research to revisit when FIPS 206 is published or batching can be done without linkability and stale roots. The first thing to measure on the branch is the sender-constrained public token, which already breaks common 8 KB header limits and is the one case where a pure encoding change helps.
