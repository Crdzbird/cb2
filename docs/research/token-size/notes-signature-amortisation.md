# Amortising or avoiding per-token post-quantum signatures (input for shrinking cb2.public)

Baseline for all byte arithmetic below: cb2.public carries Ed25519 (64 bytes) plus ML-DSA-65 (3309 bytes) = 3373 bytes of signature, which is about 4498 base64url characters of a 4883-character token. Fixed sizes used: SHA-256/BLAKE3 hash 32 bytes; ML-DSA-44 signature 2420 bytes and public key 1312 bytes ([Cloudflare, Oct 2025](https://blog.cloudflare.com/bootstrap-mtc/)); X-Wing public key 1216 bytes, ciphertext 1120 bytes, shared secret 32 bytes ([draft-connolly-cfrg-xwing-kem-11, 23 Sep 2026](https://datatracker.ietf.org/doc/draft-connolly-cfrg-xwing-kem/)).

## Merkle Tree Certificates (IETF PLANTS): batches, landmarks, signed subtrees, inclusion proofs, out-of-band distribution, experiments

### Takeaway
MTC is the most mature, deployed instance of exactly the "sign once, many objects carry a short proof" idea: a CA appends entries to a log, cosigners sign subtrees, and relying parties that have predistributed "landmark" subtree hashes accept certificates that carry only an inclusion proof (no signature at all), roughly 736 bytes at web scale; stale relying parties fall back to a "standalone" certificate that carries the proof plus full cosignatures. A Chrome plus Cloudflare experiment (2026) found landmark MTCs faster than classical certificates and clients staying fresh within hours.

### Cited Findings
- Status and authorship: draft-ietf-plants-merkle-tree-certs, PLANTS (PKI, Logs, And Tree Signatures) WG, Standards Track, editor's copy dated 5 November 2026; authors D. Benjamin (Google), D. O'Brien (Apple), B. E. Westerbaan (Cloudflare), L. Valenta (Cloudflare), F. Valsorda (Geomys) - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Revision -08 was tagged 2 November 2026; it moved the trust anchor ID definition to the separate TAI draft. Earlier revisions: -01 (Feb 2026), -03 (Apr 2026), -05 (Jul 2026), -06 (Sep 2026); -06 changed MTCSignature to a SubtreeSignature structure - [GitHub release -08](https://github.com/ietf-plants-wg/merkle-tree-certs/releases/tag/draft-ietf-plants-merkle-tree-certs-08); [-05](https://datatracker.ietf.org/doc/html/draft-ietf-plants-merkle-tree-certs-05); [-06](https://datatracker.ietf.org/doc/html/draft-ietf-plants-merkle-tree-certs-06)
- It replaced the individual draft draft-davidben-tls-merkle-tree-certs (last -10) - [datatracker](https://datatracker.ietf.org/doc/draft-davidben-tls-merkle-tree-certs/)
- Structure: the CA runs append-only issuance logs (numbered 1..65535, up to 2^48 - 1 entries each, no public submission). Each entry (TBSCertificateLogEntry) stores a hash of the subject public key rather than the key, so entries stay small even with PQ keys. The current text does not use the word "batch"; instead it uses checkpoints (full tree state at a size) and subtrees [start, end) where start is a multiple of BIT_CEIL(end - start); any interval can be covered by two such subtrees - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Signed tree heads: cosigners (the CA plus witnesses) sign a CosignedSubtree structure (12-byte label "subtree/v1\n\0", cosigner name, timestamp, log origin, start, end, 32-byte hash), designed to be compatible with the ML-DSA-44 construction in C2SP tlog-cosignature - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html); [C2SP tlog-cosignature](https://github.com/C2SP/C2SP/blob/main/tlog-cosignature.md)
- Proof size: a subtree inclusion proof has at most ceil(log2(n)) hashes of 32 bytes (SHA-256 recommended); 2^20 entries means at most 20 hashes = 640 bytes; 32 hashes (1024 bytes) covers 2^32 entries - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Draft's own size estimates (Section 6.5): standalone certificates with 2-second checkpoints cover about 3000 certs per subtree, so 12 hashes = 384 bytes of proof plus the cosignatures required by policy; landmark-relative certificates with hourly landmarks cover about 5.4 million certs, so 23 hashes = 736 bytes and no signatures - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Baseline the draft compares against: with ML-DSA-44, a conventional setup (two SCTs plus leaf signature) adds 7260 bytes; with ML-DSA-65, 9927 bytes - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Landmarks: a landmark is a tree size selected periodically (example interval `time_between_landmarks` = 1 hour); it stays active until allocation time plus `max_cert_lifetime` (example 7 days). That yields at most 169 active landmarks = 338 landmark subtrees = 10,816 bytes of relying-party state per CA with SHA-256. Errors in landmark allocation affect availability only, never cause acceptance of uncertified entries - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Out-of-band distribution: relying parties receive a predistributed, periodically updated list of trusted subtrees (browser update services are the named example); before trusting a subtree they check it is consistent with checkpoints seen by enough cosigners; a party that cannot validate the newest landmarks keeps older ones; in TLS the client advertises held landmarks via trust anchor IDs (e.g. a trust-anchor group ID covering "standalone plus landmarks 23..42 of log 8"); stale parties advertise only the CA ID and get a standalone cert - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Freshness/latency: landmark-relative certs become usable only after the next landmark is allocated and distributed ("available after a short period of time"); servers SHOULD deploy a standalone cert alongside; anyone holding a standalone cert can construct the landmark-relative one - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Revocation: by index range (minSerial / maxSerial, serial = (log_number << 48) | index); after a key compromise, revoke the index range after the compromise point while older entries stay valid; ordinary CRL/OCSP still apply - [editor's copy](https://ietf-plants-wg.github.io/merkle-tree-certs/draft-ietf-plants-merkle-tree-certs.html)
- Cloudflare/Chrome experiment announcement (28 Oct 2025, older): Cloudflare runs a "mock" MTC CA on Workers (based on its StaticCT logs), each MTC backed by a "bootstrap" certificate from a trusted CA; Chrome checks agreement before pushing landmarks; cert lifetimes "a week or so"; an up-to-date handshake needs 1 signature, 1 public key and 1 inclusion proof versus today's 5 signatures and 2 public keys (CT adds 2 signatures) - [Cloudflare blog](https://blog.cloudflare.com/bootstrap-mtc/)
- IETF 125 early results (Luke Valenta, Cloudflare, March 2026): Cloudflare TLS server for 1000 proxied domains; Chrome client on 50% of Chrome Beta 146+; classical signatures only; 7-day validity; landmarks every hour; largest proof 512 bytes (web scale projected 700-800 bytes); Chrome client landmark state about 10 KB; handshake P50 105 ms vs 116 ms (about 9% faster) and P90 348 ms vs 380 ms (about 8% faster) versus classical control; most clients pick up a new landmark within 2-3 hours; steady-state stale clients about 0.5-1.5% (an upper bound); middlebox interference a non-factor - [IETF 125 slides](https://datatracker.ietf.org/meeting/125/materials/slides-125-plants-mtc-experiment-early-results-01)
- A secondary source (certificate vendor ZoTrus) says Google plans to invite CT log operators to help guide public MTC issuance in Q1 2027; not confirmed from a Google primary source - [ZoTrus, Apr 2026](https://www.zotrus.com/en/blog/Merkle-Tree-Certificate_reshaping-Internet-security.html)

### Inferences
- For cb2, the MTC pattern maps directly: the issuer is the CA, each issued token is a log entry, the issuer (and optionally witnesses) signs subtree heads with Ed25519 plus ML-DSA-65 once per interval, and verifiers pull those signed heads in the background (like JWKS). A token then carries leaf index plus path: about 16 x 32 = 512 bytes at 2^16 tokens per landmark, 23 x 32 = 736 bytes at 5.4M. Versus 3373 bytes that is a saving of about 2600-2900 bytes (roughly 3500-3800 base64url characters), shrinking a 4883-char token to roughly 1100-1400 chars.
- The MTC lesson is that the saving only exists when the root signature is NOT in the token. A self-contained token must carry the root signature too (3373 + path), which is larger than today. So cb2 would need a dual format like MTC: a "standalone" token (path plus root signatures, larger) for verifiers without the landmark, and a "landmark-relative" token (path only) for fresh verifiers.
- Freshness cost: a landmark-relative token is not usable until the next landmark is signed and fetched by the verifier. With hourly landmarks and the 2-3 hour client update observed by Chrome, this is incompatible with short-lived access tokens (minutes) unless the interval is seconds and verifiers poll aggressively.
- MTC stores a hash of the subject key per entry; for cb2, the leaf can be a hash of the full claims so the token carries claims plus path, which is what keeps the leaf small.

### Gaps
- The precise MTC trust-distribution mechanism (Section 7.4) is not mandated by the draft; I did not find Chrome's component-updater format for landmarks.
- I did not confirm whether a later IETF 126/127 (2026) results deck with PQ (ML-DSA) MTCs exists; the IETF 125 deck is classical-only.
- The text of Appendix B onward (last about 40k characters of the draft) was not read.

## Batch signing for tokens (sign a Merkle root over N tokens in a window) and prior art (TLS batch signing, CT, Sigstore/Rekor, Key Transparency)

### Takeaway
Batch signing (one signature over a Merkle root, each message carries index plus log2(N) sibling hashes) is well analysed and cheap (about 17 hashes = 544 bytes for N = 2^16 with the TLS draft's blinded-leaf layout), but on its own it only amortises signing CPU, not token size, because each self-contained output still includes the root signature; it shrinks tokens only when combined with out-of-band distribution of signed roots (the MTC, CT, Rekor and Key Transparency pattern).

### Cited Findings
- draft-ietf-tls-batch-signing-00 (D. Benjamin, 13 Jan 2020, Experimental, now expired; older info): one signing operation serves many requests "at a logarithmic cost to signature size"; for n messages level 0 has 2n leaves: even positions Hash(0x00 || msg), odd positions random blinding values of hash length (to keep other messages confidential); BatchSignature = uint32 index + path of l - 1 sibling hashes (l = ceil(log2 n) + 2) + root_signature over a context string "TLS batch signature"; verifiers reject index >= 2^31 or path > 32 elements - [datatracker](https://datatracker.ietf.org/doc/html/draft-ietf-tls-batch-signing)
- The same draft's privacy considerations: two signatures with the same root are linkable; a signature reveals batch size rounded up to a power of two; mitigation is to partition contexts in which requests may be batched; it gives no guidance on how long to wait to fill a batch - [datatracker](https://datatracker.ietf.org/doc/html/draft-ietf-tls-batch-signing)
- Predecessor draft-davidben-tls-batch-signing-00 (July 2019) - [datatracker](https://datatracker.ietf.org/doc/draft-davidben-tls-batch-signing/00/)
- "Batch Signatures, Revisited" (Aguilar-Melchor, Albrecht, Bailleux, Bindel, Howe, Huelsing, Joseph, Manzano; ePrint 2023/492, CT-RSA 2024, LNCS 14643): batching lets slow PQ signers reach high throughput with a mild latency increase - [ePrint 2023/492](https://eprint.iacr.org/2023/492)
- SandboxAQ summary (2 May 2023, older): batching 32 messages adds under 100 bytes per signature (2536 bytes total with Dilithium2); throughput +72% Dilithium2, +54% Falcon-512, +467% SPHINCS+-128; latency increase under 25%; tested N = 16 and 32; best N depends on scheme - [SandboxAQ blog](https://cryptographycaffe.sandboxaq.com/posts/batch-signing/)
- draft-joseph-tls-batch-signatures-00 (SandboxAQ, Nov 2023, individual, Informational; older) - [draft text](https://potaroo.net/ietf/ids/draft-joseph-tls-batch-signatures-00.html)
- C2SP tlog-cosignature: witnesses verify consistency proofs against their saved latest tree head and cosign; Ed25519 cosignature = 8-byte timestamp + 64-byte signature over a text checkpoint; ML-DSA-44 cosignatures support both checkpoints and subtrees and "SHOULD be used for new deployments" - [C2SP](https://github.com/C2SP/C2SP/blob/main/tlog-cosignature.md)
- CT/MTC fact: CT SCTs promise inclusion within 24 hours (illustrates batch latency of log-based systems) - [Cloudflare blog](https://blog.cloudflare.com/bootstrap-mtc/)
- Sigstore Rekor v2 (per NVIDIA AICR docs, not Sigstore primary): tile-backed log (C2SP tlog-tiles, Trillian-Tessera), yearly shards (e.g. log2025-1.rekor.sigstore.dev), bundles embed the entry, its inclusion proof and checkpoint origin; no inline signed timestamp so an RFC 3161 TSA is required; witnessing built in; Cosign v3.0.1+ needed - [NVIDIA AICR docs](https://docs.nvidia.com/aicr/latest/contributor-guide/rekor-v-2-signing)
- WhatsApp Key Transparency (Apr 2023, older): Auditable Key Directory (AKD, open-source Rust, SEEMless/Parakeet lineage), NCC Group audit Aug 2023; Cloudflare independently verifies AKD audit proofs (append-only consistency of epochs) - [Meta engineering](https://engineering.fb.com/2023/04/13/security/whatsapp-key-transparency/); [facebook/akd](https://github.com/facebook/akd); [Cloudflare](https://blog.cloudflare.com/key-transparency)
- Apple iMessage Contact Key Verification (Oct 2023, older): CONIKS-style verifiable log-backed map; Signed Mutation Timestamps as promises of inclusion; devices verify inclusion and consistency proofs and gossip log hashes inside a small percentage of encrypted messages to detect split views - [Apple Security Research](https://security.apple.com/blog/imessage-contact-key-verification/)

### Inferences
- Size per token with the TLS-draft layout at N = 2^16: index 4 bytes + 17 hashes (16 levels plus the blinding sibling) = 548 bytes, about 731 base64url chars. Using a keyed per-leaf nonce derived from the leaf content (or committing claims with a random salt inside the leaf) the blinding level can be dropped: 4 + 512 = 516 bytes. Truncating hashes is unsafe for second-preimage reasons below 32 bytes at 128-bit PQ-level targets (collision resistance with Grover-style or classical birthday is the concern), so 32 bytes per level should be kept.
- Latency: fixed time windows bound the wait (e.g. 100 ms to 1 s windows; at low load a window yields a tiny tree and a short path, so size self-adjusts with log2 of actual volume). Combined with out-of-band roots, the binding latency is root publication plus verifier fetch, not signing.
- Privacy: tokens from the same window are linkable by root and reveal issuance volume per window; for user-facing tokens, partition batches per tenant/audience and pad trees to a fixed size.
- Transparency is a bonus: if roots are published as an append-only log with witness cosignatures (tlog-cosignature), cb2 gets issuance transparency (detect a compromised issuer minting tokens) for free, as CT/KT do.

### Gaps
- No public source found for a token system (JWT/PASETO/Macaroons) that ships Merkle-batched signatures with out-of-band roots; the closest are MTC, CT, Rekor and KT.
- No authoritative measurement found of "optimal window length" for token issuance; values above are design suggestions, not sourced.
- Did not find a Sigstore primary spec page for the Rekor v2 proof format.

## Verifier-cached signatures: signed short-lived delegated key (classical signature or MAC) checked per token

### Takeaway
RFC 9345 delegated credentials are the standard template: a long-term key signs a short-lived credential (default max 7 days) carrying a different public key, and per-connection signatures use that key; the cost is that a stolen delegated key can be used until expiry and there is no early revocation. Applied to cb2, the issuer would sign a delegated key once with Ed25519 plus ML-DSA-65, verifiers cache it, and tokens carry only a cheap tag; the choice of what that cheap tag is decides whether post-quantum unforgeability survives.

### Cited Findings
- RFC 9345 "Delegated Credentials for TLS and DTLS" (July 2023; Barnes, Iyengar, Sullivan, Rescorla), Standards Track - [RFC 9345](https://www.rfc-editor.org/rfc/rfc9345.html)
- Credential = valid_time (32-bit seconds from the delegation cert's notBefore) + dc_cert_verify_algorithm + DER SubjectPublicKeyInfo; DelegatedCredential = cred + algorithm + signature by the end-entity key over a context string, the certificate and the credential - [RFC 9345](https://www.rfc-editor.org/rfc/rfc9345.html)
- Default maximum validity 7 days; must not exceed the delegation certificate's validity - [RFC 9345](https://www.rfc-editor.org/rfc/rfc9345.html)
- Security: a stolen delegated private key lets the attacker impersonate until expiry but not mint new credentials; there is no early revocation mechanism for delegated credentials; revoking the end-entity certificate implicitly revokes them - [RFC 9345](https://www.rfc-editor.org/rfc/rfc9345.html)
- AuthKEM-PSK (draft-wiggers-tls-authkem-psk-05, May 2026) covers abbreviated handshakes when the client already holds the server's long-term KEM key, i.e. a cached-key model - [draft-wiggers-tls-authkem-psk-05](https://www.ietf.org/ietf-ftp/internet-drafts/draft-wiggers-tls-authkem-psk-05.html)

### Inferences
- Option A, delegated classical key: issuer signs (Ed25519 + ML-DSA-65) a credential binding a short-lived Ed25519 key with a validity of hours; verifiers fetch and cache it (one 3.4 KB check per key rotation); each token carries an Ed25519 signature (64 bytes) plus a key id. Token signature overhead drops from 3373 to about 72 bytes. Trade-off: per-token authenticity is only classical. Forgery requires breaking Ed25519 while the delegated key is valid, so a "forge later" quantum attacker gains nothing after expiry; a real-time CRQC would break it. This is a reasonable interim posture but not equivalent to current cb2.public guarantees.
- Option B, delegated symmetric key per verifier: issuer wraps a per-verifier MAC key to the verifier's X-Wing key with kcb2.seal (1120-byte ciphertext, sent once out of band or in the first token), signs the wrapped blob with Ed25519 + ML-DSA-65 once, and thereafter emits cb2.local-style tokens with a 32-byte keyed BLAKE3 tag. Per-token overhead about 32 bytes plus key id, fully post-quantum (X-Wing + ML-DSA-65 + 256-bit MAC). Trade-off: the token becomes audience-specific and non-transferable; any holder of the MAC key (the verifier) can forge tokens to itself, so it is unsuitable where third parties must verify or where verifiers are not trusted not to mint.
- Option C, hybrid of A and MTC: signed batch roots fetched by verifiers per interval are equivalent to a "delegated credential" whose content is a Merkle root rather than a key; this keeps full PQ unforgeability (hash-based paths) and third-party verifiability at about 0.5-0.7 KB per token, unlike A (classical) or B (designated verifier).
- Revocation/compromise windows: A and B inherit RFC 9345's "valid until expiry" property; rotate delegated keys at the token lifetime or shorter, and allow verifiers to drop a key id via the same channel that distributes keys (JWKS-like). In MTC-style roots, compromise is handled by revoking index ranges.

### Gaps
- No standard found for "signed key once, MAC thereafter" in token formats (JWT/PASETO); Privacy Pass and similar systems were not researched here.
- RFC 9345 is TLS-specific; no RFC profile for delegated keys in JOSE/COSE was located.

## KEM-based authentication instead of signatures (KEMTLS, AuthKEM, deniable/designated-verifier constructions)

### Takeaway
KEM-based authentication (KEMTLS, AuthKEM) replaces a signature with a KEM ciphertext to the verifier's public key plus a MAC: per message it costs about 1088 bytes (ML-KEM-768) or 1120 bytes (X-Wing) plus a 32-byte tag, versus 3373 bytes, but it authenticates only to the designated holder of the KEM private key, and needs that key in advance. For tokens with a known audience it is effectively "cb2.local keyed by kcb2.seal", and its main size win comes from amortising the encapsulation across many tokens per verifier.

### Cited Findings
- AuthKEM (draft-celi-wiggers-tls-authkem-07, 4 May 2026, Informational, TLS WG area, not adopted; authors Wiggers, Celi, Schwabe, Stebila, Sullivan; -08 exists): the client encapsulates to the server's certificate KEM public key, only the holder of the private key can derive the secret, which is mixed into the key schedule; server authentication is implicit until its Finished; client authentication via AuthKEM needs an extra round trip; code points experimental - [draft -07](https://datatracker.ietf.org/doc/html/draft-celi-wiggers-tls-authkem-07)
- AuthKEM size table (bytes; omits hybrids, CT, OCSP): TLS 1.3 with Dilithium-2 handshake auth 3732 + Dilithium-2 chain 6152 = 9884; AuthKEM with Kyber-768 handshake auth 2272 + Dilithium-2 chain 6152 = 8424; with Falcon-512 chain, AuthKEM 4564 vs TLS 1.3 Falcon 3792 - [draft -07](https://datatracker.ietf.org/doc/html/draft-celi-wiggers-tls-authkem-07)
- Draft -05 notes the certificate chain still dominates handshake size - [draft -05](https://datatracker.ietf.org/doc/html/draft-celi-wiggers-tls-authkem-05)
- AuthKEM-PSK (draft-wiggers-tls-authkem-psk-05, May 2026): abbreviated handshake when the client already has the server's KEM key - [draft](https://www.ietf.org/ietf-ftp/internet-drafts/draft-wiggers-tls-authkem-psk-05.html)
- X-Wing: pk 1216, ct 1120, ss 32, sk 32 bytes; draft-11, 23 Sep 2026, independent stream - [datatracker](https://datatracker.ietf.org/doc/draft-connolly-cfrg-xwing-kem/)
- Designated-verifier signatures from KEM + MAC: Ebrahimi (ePrint 2024/128) builds a non-transferable designated verifier signature from an IND-CCA KEM, one-way PKE, a MAC and a signature - [ePrint 2024/128](https://eprint.iacr.org/2024/128.pdf)
- Brendel, Fiedler, Guenther, Janson, Stebila (PKC 2022) combine KEMs with designated verifier signatures for post-quantum deniable asynchronous key exchange - [Stebila page](https://www.douglas.stebila.ca/research/papers/PKC-BFGJS22); [ePrint 2021/769](https://eprint.iacr.org/2021/769/20210804:094732)
- K-Waay (USENIX Security 2024): split-KEM implicit authentication for a PQ X3DH alternative without ring signatures; notes PQXDH gives PQ confidentiality but not PQ authentication - [USENIX paper](https://usenix.org/system/files/usenixsecurity24-collins.pdf); [ePrint 2024/120](https://eprint.iacr.org/2024/120.pdf)

### Inferences
- Per-token KEM auth for cb2: X-Wing ciphertext 1120 + 32-byte tag = 1152 bytes (about 1536 base64url chars), saving about 2220 bytes vs 3373. But the issuer must also prove the encapsulation came from it; a bare KEM ciphertext authenticates the receiver, not the sender. Sender authentication requires either the issuer's static KEM key in a two-KEM (KEMTLS-style mutual) construction, a pre-shared issuer key, or a one-time signature over the issuer-to-verifier key, which is what Option B in the previous section does.
- Amortised version is strictly better: encapsulate once per (issuer, verifier, epoch), cache the derived MAC key on both sides, then each token is a cb2.local token with a 32-byte tag and a key id. This is the "public token becomes per-audience local token" transformation; it requires the audience to be known at issuance and gives designated-verifier (deniable, non-transferable) semantics.
- Multi-audience tokens can carry one 32-byte tag per audience (e.g. 5 audiences = 160 bytes), still far below 3373 bytes.
- Holder proofs (sender-constrained tokens) are orthogonal: they bind presentation to the holder key, but issuer authenticity still needs one of the mechanisms above.

### Gaps
- No standardised KEM-based authenticated-token format (JOSE/COSE/PASETO) was found.
- HPKE Auth mode was not researched here; its standard Auth mode uses DHKEM (classical), so it would not give PQ sender authentication.

## Aggregate and multi-signatures for PQ schemes; stateful hash-based signatures

### Takeaway
PQ signature aggregation exists only as research prototypes based on lattice proof systems (LaBRADOR, lattice SNARKs) aggregating Falcon signatures into tens of kilobytes for thousands of signatures; it targets blockchains with many signers, not one issuer signing many tokens, so it does not help cb2 (one issuer, independent verification of each token). Merkle batching is the relevant "aggregation" for a single signer.

### Cited Findings
- Aardal, Aranha, Boudgoust, Kolby, Takahashi, "Aggregating Falcon Signatures with LaBRADOR" (CRYPTO 2024): first complete knowledge-soundness analysis for non-interactive LaBRADOR and concrete aggregate size estimates - [publication page](https://dfaranha.github.io/publication/aardalabkt24); [IACR news](https://iacr.org/news/item/22624)
- PSE blog: Falcon plus LaBRADOR aggregation - [PSE](https://pse.dev/blog/post-quantum-signature-aggregation-with-falcon-and-LaBRADOR)
- Ethereum research: about 74 KB proof for 10,000 Falcon signatures; batches under 2000 do better with modulus 2^40 - [ethresear.ch](https://ethresear.ch/t/lattice-based-signature-aggregation/22282)
- PQScale (BTQ, vendor claim): 1722 Falcon signatures aggregate to about 94 KB, under 9% of the raw size - [BTQ](https://btq.com/news/introducing-pqscale-a-scaling-solution-for-post-quantum-signatures)
- Lemur+ (ePrint 2026/2054): PQ synchronized multi-signature on LaBRADOR, aggregate size from 491 KB to about 56 KB - [ePrint 2026/2054](https://eprint.iacr.org/2026/2054.pdf)
- a16z "Aerie" (Oct 2026, secondary coverage only): lattice SNARK aggregation, about 66 KiB proofs independent of batch size, 16,384 Falcon-1024 signatures in 0.63 s - [Crowdfund Insider](https://www.crowdfundinsider.com/?p=319009); unverified against the primary a16z article
- C2SP tlog-cosignature recommends ML-DSA-44 for new witness deployments (i.e. witness quorums still use independent signatures, not aggregation) - [C2SP](https://github.com/C2SP/C2SP/blob/main/tlog-cosignature.md)

### Inferences
- Aggregate signatures compress many signatures into one object verified together; a cb2 verifier checks one token at a time, so aggregation gives nothing per token. Their floor (tens of KB) is also far above 3373 bytes.
- Stateful hash-based signatures (LMS/XMSS) are relevant only as the root signer in a batch/MTC design (the issuer signs few roots, so state management is easy), but they do not shrink tokens on their own (LMS/XMSS signatures are kilobytes); not researched further.

### Gaps
- No primary source for Aerie numbers; no ML-DSA (as opposed to Falcon) aggregation results found.
- LMS/XMSS sizes not sourced in this pass.
