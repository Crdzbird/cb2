# Compression inside authentication tokens and its security consequences

Research date: 2026-11-07. Items dated before 2025 are marked "(older)". All byte figures for cb2 come from the measurement in the assignment: 217-byte JSON claims, 161 bytes with plain zstd, 62 bytes average with a dictionary trained on 4000 claim sets, compressed range 55 to 76 bytes.

## 1. JWE "zip":"DEF", why JWS has no compression, RFC 8725 guidance, and the decompression-bomb CVEs

### Takeaway
JOSE allows compression only in JWE (RFC 7516 "zip":"DEF"), RFC 8725 later said compression before encryption SHOULD NOT be done, and in 2024 nearly every major JOSE library shipped a decompression-bomb fix. The fixes were a 250 kB cap on decompressed output or token length (python-jose, jose, go-jose, jwcrypto, jose4j, Microsoft), sometimes a ratio limit (go-jose: 10x), and in one case removal of compression altogether (panva/jose v5).

### Cited Findings
- RFC 7516 section 4.1.3 defines "zip" as the compression algorithm "applied to the plaintext before encryption", with the only registered value "DEF" (DEFLATE, RFC 1951). It "MUST be integrity protected" and so may only appear in the JWE Protected Header. The IANA registration lists its usage location as JWE only. The RFC 7516 security considerations (11.1 to 11.5) say nothing about compression or length leakage. - [RFC 7516](https://www.rfc-editor.org/rfc/rfc7516.html)
- Why JWS has no "zip" (older, Dec 2012): in a JOSE WG thread, Mike Jones measured that adding "zip":"DEF" to a JWS header cost 16 characters and that the compressed then base64url-encoded payload was still larger than the original. He called zip "suboptimal" compared with not double-base64url-encoding the payload. A reply argued deflate saved about 11% (526 to 427 bytes) on the sample. The payload under test was already-encrypted JWE output, which does not compress. - [JOSE list msg01094](https://mail-archive.com/jose@ietf.org/msg01094.html), [msg01098](https://mail-archive.com/jose@ietf.org/msg01098.html), [msg01103](https://www.mail-archive.com/jose@ietf.org/msg01103.html), [msg01104](https://mail-archive.com/jose@ietf.org/msg01104.html)
- RFC 8725 (JWT BCP, 2020) section 2.4 "Plaintext Leakage through Analysis of Ciphertext Length": the problem "is exacerbated when the plaintext is initially compressed", because compressed length depends on content, and "Compression attacks are particularly powerful when there is attacker-controlled data". Section 3.6 "Avoid Compression of Encryption Inputs": "Compression of data SHOULD NOT be done before encryption, because such compressed data often reveals information about the plaintext." - [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)
- python-jose, CVE-2024-33664 (affects up to 3.3.0): JWE decompression bomb. The fix (PR #352, merged 6 Feb 2025) adds `JWE_SIZE_LIMIT = 250 * 1024`, rejects incoming JWE strings over that size, and uses a bounded `zlib.decompressobj()` so no more than 250 KB is inflated, else `JWEError`. - [python-jose PR #352](https://github.com/mpdavis/python-jose/pull/352), [openSUSE patch](https://src.opensuse.org/pool/python-python-jose/src/branch/devel/CVE-2024-33664.patch), [GHSA-cjwg-qfpm-7377](https://github.com/advisories/GHSA-cjwg-qfpm-7377)
- jwcrypto, CVE-2024-28102 (GHSA-j857-7rvv-vj97), fixed in 1.5.6: "JWT bomb" via high-ratio compressed JWE. The fix did not change decompression, it capped the maximum token length. CVSS 3.1 6.8, CWE-770. - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-28102), [Red Hat](https://access.redhat.com/security/cve/CVE-2024-28102)
- go-jose, CVE-2024-28180 (GHSA-c5q2-7r4c-mv6g): Decrypt/DecryptMulti now fail once output exceeds 250 kB or 10x the compressed size, whichever is larger. Fixed in v4.0.1, v3.0.3, v2.6.3. CVSS 4.3, CWE-409. - [GitLab advisory (v3)](https://advisories.gitlab.com/golang/github.com/go-jose/go-jose/v3/CVE-2024-28180/), [v4](https://advisories.gitlab.com/pkg/golang/github.com/go-jose/go-jose/v4/CVE-2024-28180/)
- panva/jose (npm), CVE-2024-28176 (GHSA-hhhv-q57g-882q, 7 Mar 2024): fixed in 2.0.7 and 4.15.5 by limiting decompression to 250 kB of plaintext (tunable via `inflateRaw` in v4 or `inflateRawSyncLimit` in v2). The advisory notes the token length is set by the compressed size, so it "can fall below application-defined limits", defeating other resource-exhaustion defenses. v5.x "removed support for compressed payloads entirely". Suggested workaround: reject any JWE whose protected header contains "zip". - [GHSA-hhhv-q57g-882q](https://github.com/advisories/GHSA-hhhv-q57g-882q)
- lestrrat-go/jwx, CVE-2024-28122: fixed in 1.2.29 and 2.0.21 by limiting decompressed size. CVSS 6.8. - [GitLab advisory](https://advisories.gitlab.com/golang/github.com/lestrrat-go/jwx/CVE-2024-28122/), [Go vulndb GO-2024-2632](https://go.googlesource.com/vulndb/+/d02edb6cf6631b9bd3e1e246055ce71f61b39b95/data/osv/GO-2024-2632.json)
- jose4j, CVE-2024-29371: fixed in 0.9.6 (some NVD text says 0.9.5). CVSS 7.5 (A:H, no privileges). The upstream issue recommends a 250K token-length cap, "also adopted by" Microsoft System.IdentityModel.Tokens.Jwt for CVE-2024-21319. - [GitLab advisory](https://advisories.gitlab.com/pkg/maven/org.bitbucket.b_c/jose4j/CVE-2024-29371/), [jose4j issue 220](https://bitbucket.org/b_c/jose4j/issues/220/vuln-zip-bomb-attack)
- Nimbus JOSE+JWT: issue #545, "JWEObject.decrypt must reject compressed ciphertexts that are too large", proposed a 100K-character cap on the ciphertext of compressed JWEs after "a recent sec audit". It is marked resolved. A user with large payloads objected, and the maintainer looked into making it configurable. - [Nimbus issue 545](https://bitbucket.org/connect2id/nimbus-jose-jwt/issues/545/jweobjectdecrypt-must-reject-compressed)
- jose2go has a similar deflate bomb, CVE-2025-63811, fixed in 1.7.0. - [Miggo CVE-2025-63811](https://www.miggo.io/vulnerability-database/cve/CVE-2025-63811)

### Inferences
- The 2024 CVE wave targeted the decrypting side: whoever holds a key that produces a valid JWE (any public-key holder for ECDH-ES/RSA JWE) can force an inflate. For cb2.local (symmetric) only key holders can mint, so the bomb is mainly a concern if cb2 decompresses before verifying the BLAKE3 MAC. Verify first, then decompress with a hard output cap equal to the maximum claim size.
- The fix pattern most libraries converged on (a hard 250 kB output cap plus a ratio check) is generous for cb2. A cap near the largest legal claim set (a few KB) is safer and cheaper.
- panva/jose dropping zip in v5 and RFC 8725 3.6 both show the ecosystem moving away from compressed encrypted tokens. A cb2 compression feature runs against that consensus and must justify itself with padding (section 3).

### Gaps
- No node-jose (Cisco) decompression advisory was found. Search returned nothing.
- Exact Nimbus release that implemented #545 and its final default limit were not confirmed.
- The JOSE WG's official rationale for keeping "zip" out of RFC 7515 was not found in the RFC text. Only the 2012 list thread was found.

## 2. Compression side channels: CRIME, BREACH, HEIST, and when a token is exploitable

### Takeaway
Every known compression oracle needs three things together: attacker-influenced data compressed in the same context as a secret, repeated observation of the resulting length, and many adaptive queries. A cb2.local token with attacker-influenced claims (username, email, requested scopes, free-text claims) next to secret claims, re-issued on demand with its length visible, meets all three. The 55 to 76 byte spread in the measurement shows the length already depends on values.

### Cited Findings
- CRIME (Duong and Rizzo, Sept 2012, older) used the compression ratio of TLS-compressed requests to recover secrets such as cookies. Disabling TLS-level compression fully mitigates it. - [Wikipedia: BREACH (CRIME background)](https://en.wikipedia.org/wiki/BREACH), [Help Net Security history](https://www.helpnetsecurity.com/2016/08/11/compression-oracle-attacks-https/)
- BREACH (Gluck, Harris, Prado, Black Hat USA Aug 2013, older) applies CRIME to HTTP-level gzip/DEFLATE response bodies, so disabling TLS compression does not help. Mitigations, ranked: disable HTTP compression, separate secrets from user input, randomize secrets per request (masking), length hiding, rate limiting. - [BREACH paper](https://css.csail.mit.edu/6.566/2014/readings/breach.pdf), [Wikipedia](https://en.wikipedia.org/wiki/BREACH)
- HEIST (Vanhoef and Van Goethem, Black Hat USA 2016, older) measures response sizes from browser JavaScript using TCP-window timing, removing BREACH/CRIME's need for a network position. It works over HTTP/1.x and HTTP/2, and was demonstrated from an ad script. The authors found few effective countermeasures beyond blocking third-party cookies. - [HEIST slides](https://www.blackhat.com/docs/us-16/materials/us-16-VanGoethem-HEIST-HTTP-Encrypted-Information-Can-Be-Stolen-Through-TCP-Windows.pdf), [The Register](https://www.theregister.com/2016/08/05/javascript_heist_attack_https/)
- TLS 1.3 removed compression: "For every TLS 1.3 ClientHello, this vector [legacy_compression_methods] MUST contain exactly one byte, set to zero" (null compression). - [RFC 8446 section 4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2)
- HPACK and QPACK threat model: an attacker who "can both define fields to be encoded and transmitted and observe the length of those fields once they are encoded" can probe the compression context. Each probe only confirms a guess, so high-entropy values are safe but "values with low entropy remain vulnerable". - [RFC 7541 section 7.1](https://www.rfc-editor.org/rfc/rfc7541.html#section-7.1), [RFC 9204 section 7.1](https://www.rfc-editor.org/rfc/rfc9204.html#section-7.1)
- RFC 9842 (dictionary transport) warns that "it's a bad idea to compress data from mixed (e.g., public and private) sources", and that "if secret cookies are compressed using a public-data-only dictionary, information about the cookies is still leaked". - [RFC 9842 section 9](https://www.rfc-editor.org/rfc/rfc9842.html)
- RFC 8725 section 2.4 says compression attacks are "particularly powerful when there is attacker-controlled data". - [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)

### Inferences
- Exploitable for cb2.local when all of these hold: (a) one claim is attacker-influenced, such as a display name, email, `sub` the attacker picks, requested scope, or a value echoed from a request; (b) another claim in the same compressed stream is secret and low-entropy or guessable in chunks, such as role, tenant id, internal user id, feature flags, or a PII field; (c) the attacker obtains many tokens with chosen inputs and sees each length. Seeing the length is trivial because the token is usually handed to its own subject or visible in transit, and the base64url length shows ciphertext length to the byte.
- A trained dictionary makes the oracle sharper, not weaker: a guess that matches a dictionary string or an earlier claim value costs a few bits instead of a literal, so length differences per correct guess grow. The measured 21-byte spread (55 to 76) for realistic claims is the signal an attacker would mine.
- Not exploitable when the token's subject is the only one who can influence claims and every claim is already known to them (no secrets from the holder), or when no claim is attacker-influenced. Many access tokens fit this case, but a library cannot know it, so the default must be safe.
- cb2.public is not exposed to the length leak: signed claims are readable in the clear, so length reveals nothing new. Only the decompression-bomb risk from section 1 applies there.

### Gaps
- No published attack on compressed JWE or other compressed tokens in the wild was found. The risk is argued by analogy (RFC 8725, BREACH) rather than demonstrated.
- BREACH's exact request counts and timing ("SSL, gone in 30 seconds") were not verified from the paper text.

## 3. Mitigations: padding, PADME, fixed size, field separation, and operation order

### Takeaway
The only robust fix for the length oracle is to make the encrypted length independent of claim values: pad the compressed plaintext to one fixed size (or a few coarse buckets chosen by non-secret structure) before encryption. PADME is too fine-grained at 55 to 76 bytes. Order must be compress, pad, encrypt, MAC on issue, and verify MAC, decrypt, unpad, bounded decompress on verify.

### Cited Findings
- PADME (Nikitin et al., PoPETs 2019, older) pads to a set of lengths with at most 12% overhead (bound 1/(2 log2 L)), leaking O(log log M) bits of length. On real datasets it averaged about 3% overhead and cut the share of uniquely identifiable Ubuntu packages from 83% to 3%. - [PoPETs 2019](https://petsymposium.org/popets/2019/popets-2019-0056.php), [arXiv 1806.03160](https://arxiv.org/pdf/1806.03160)
- PADME applied to the cb2 numbers (computed here with the paper's algorithm): compressed lengths 55 to 76 map to five buckets {56, 60, 64, 72, 80}. Buckets are 4 bytes wide below 64 and 8 bytes from 64 up. 62 maps to 64, 217 to 224, 161 to 176. - computed locally from the PADME definition in [arXiv 1806.03160](https://arxiv.org/pdf/1806.03160)
- Signal pads message bodies to a multiple of `PADDING_BLOCK_SIZE = 80` bytes with a 0x80 terminator. - [Signal-Android PushTransportDetails.java](https://github.com/signalapp/Signal-Android/blob/main/lib/libsignal-service/src/main/java/org/whispersystems/signalservice/internal/push/PushTransportDetails.java)
- Rack's encrypted session cookie (`Rack::Session::Encryptor`) offers optional deflate via `:gzip_over` (compress messages over N bytes) together with `:pad_size`, padding encrypted data to a multiple of N bytes (default 32, valid range 2 to 4096) with random bytes and a 2-byte pad-length prefix. - [rack-session cookie.rb](https://github.com/rack/rack-session/blob/main/lib/rack/session/cookie.rb), [rack-session encryptor.rb](https://github.com/rack/rack-session/blob/main/lib/rack/session/encryptor.rb)
- Django `signing.dumps(compress=True)` uses zlib only when it is smaller, marks this with a leading "." that "is included in the signature, to protect against zip bombs", and verifies the signature before decompressing. This is compress-then-sign with the format flag authenticated. - [Django signing.py 4.2.4](https://github.com/django/django/blob/4.2.4/django/core/signing.py)
- BREACH lists "separating secrets from user input" and per-request secret masking as mitigations. - [BREACH paper](https://css.csail.mit.edu/6.566/2014/readings/breach.pdf)
- RFC 9842 suggests "disabling compression when any portion of the content comes from uncontrolled sources". - [RFC 9842 section 9](https://www.rfc-editor.org/rfc/rfc9842.html)
- HPACK/QPACK mitigation: never-indexed literals for sensitive fields, and noting that "short or low-entropy values are more readily recovered". - [RFC 7541 section 7.1.3](https://www.rfc-editor.org/rfc/rfc7541.html#section-7.1.3)

### Inferences
- Fixed-size output for cb2.local: pad every dictionary-compressed claim set to one size L (for this distribution 80 bytes covers the observed maximum of 76 plus a 1 to 2 byte length prefix, with margin needed for the tail). Average cost is about 18 bytes over 62, still 137 bytes below the 217-byte raw claims. Raw-byte to base64url: 62 becomes 83 chars, 80 becomes 107 chars, 217 becomes 290 chars. If a claim set compresses beyond L, either fall back to a larger fixed class (for example 128, 256, 512) chosen by a deterministic, non-secret rule, or reject. The class then leaks at most about 2 bits, and only on unusual inputs.
- PADME's five buckets in the 55 to 76 range leak about 2.3 bits per token. In an adaptive probing setting that is enough to confirm guesses one at a time, so PADME alone is not adequate for compress-then-encrypt with attacker-influenced claims. It is aimed at hiding file sizes, not at stopping chosen-plaintext oracles.
- Compressing only non-secret fields: split claims into a "public or structural" part (keys, iss, aud, typ, timestamps) that is dictionary-compressed and a "sensitive or attacker-influenced" part encoded raw (no shared compression context). Most of the measured gain probably comes from keys and fixed strings the dictionary removes, which leak nothing. This is safer but needs a schema or a field allowlist.
- Order: compress, then pad, then encrypt and MAC (XChaCha20 then keyed BLAKE3 over header and ciphertext) on issue. On verify: MAC check, decrypt, check and strip padding, then decompress with a bounded output buffer, with the dictionary id taken only from the authenticated header. MAC-before-compress (MAC the plaintext, then compress) would force decompression of unauthenticated data and reopen the bomb. For cb2.public the same rule applies: sign the compressed bytes and verify Ed25519 and ML-DSA-65 before inflating.
- Timestamps (`iat`, `exp`) and random `jti` values are high-entropy and resist compression. They mostly add variance, but they do not hide the secret-dependent part of the variance, so padding is still needed.

### Gaps
- No published analysis was found that sizes padding buckets specifically for tokens or cookies. The 80-byte figure is extrapolated from the single measured distribution and must be rechecked on production-shaped claim sets, including the tail.

## 4. Trained dictionaries for tiny messages: zstd, brotli, RFC 9842, ids and raw framing

### Takeaway
Dictionaries are the only way generic compressors help at about 200 bytes. zstd reports 2x to 5x better small-data ratios with a dictionary, and the measured 217 to 62 bytes (3.5x, versus 1.35x without) is in line. For tokens, strip all zstd framing (magicless, no checksum, no dictID, no content size) and carry a short dictionary version in cb2's own authenticated header, not RFC 9842's 32-byte SHA-256 dictionary hash.

### Cited Findings
- zstd README: "Training works if there is some correlation in a family of small data samples"; "Dictionary gains are mostly effective in the first few KB"; dictionaries give better ratios "while simultaneously providing faster compression and decompression speeds". Silesia speeds with zstd 1.5.7 on i7-9700K: level -1 ratio 2.896 at 510 MB/s compress and 1550 MB/s decompress; --fast=1 at 545/1850 MB/s. - [zstd README](https://github.com/facebook/zstd/blob/dev/README.md)
- Facebook engineering blog (31 Aug 2016, older): with dictionaries "small data compression can range anywhere from 2x to 5x better". On 1,000 GitHub user records (about 850 KB raw), per-file gzip or zstd gave just over 300 KB (2.8x), and zstd with a dictionary gave 122 KB (6.9x). - [Facebook Engineering](https://engineering.fb.com/2016/08/31/core-infra/smaller-and-faster-data-compression-with-zstandard/)
- zstd frame header: at least 6 bytes in standard format (4-byte magic, frame descriptor, window byte), 2 bytes in magicless format when `ZSTD_c_format = ZSTD_f_zstd1_magicless`, `ZSTD_c_contentSizeFlag = 0`, `ZSTD_c_checksumFlag = 0`, `ZSTD_c_dictIDFlag = 0`. Magicless output only round-trips with a decoder configured for magicless. Block-level APIs (deprecated) were described as avoiding about 12 bytes of frame metadata, "non-negligible" under 100 bytes. - [zstd-sys docs (ZSTD_getBlockSize)](https://docs.rs/zstd-sys/2.0.13+zstd.1.5.6/zstd_sys/fn.ZSTD_getBlockSize.html), [structured-zstd FrameCompressor](https://docs.rs/structured-zstd/0.1.1/structured_zstd/encoding/struct.FrameCompressor.html)
- RFC 9842 (Compression Dictionary Transport, Proposed Standard, Sept 2025, Meenan and Weiss): `Available-Dictionary` carries the SHA-256 hash of one dictionary. The "dcb" (dictionary-compressed Brotli) header is 36 bytes (4-byte magic FF 44 43 42 plus a 32-byte SHA-256). The "dcz" (dictionary-compressed zstd) header is 40 bytes (8-byte skippable-frame magic plus a 32-byte SHA-256). Dictionaries are same-origin only, compression "MUST only be used when both the dictionary and the compressed response are fully readable", and clients "MUST treat dictionaries in the same way that they treat cookies". - [RFC 9842](https://www.rfc-editor.org/rfc/rfc9842.html), [datatracker](https://datatracker.ietf.org/doc/rfc9842/)
- Rollout: Chrome and Edge 130 shipped Compression Dictionary Transport (late 2024). Google Search began using shared Brotli dictionaries in spring 2025 and reported a 23% average HTML reduction versus standard Brotli across all Chrome users. One example went from 107 kB to 60 kB. - [Chrome blog: Search compression dictionaries](https://developer.chrome.com/blog/search-compression-dictionaries), [Chrome blog: shared dictionary compression](https://developer.chrome.com/blog/shared-dictionary-compression), [MDN guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Compression_dictionary_transport)
- DebugBear measured up to 76% reduction with shared dictionaries, for example zstd level 3 going from about 34 KB to about 13 KB. - [DebugBear](https://www.debugbear.com/blog/shared-compression-dictionaries)

### Inferences
- Wire budget for cb2: the 62-byte average likely includes zstd frame overhead unless magicless with flags off was already used. A magicless, flag-free frame is 2 bytes of header, so the standard header plus a 4-byte dictID plus content size can add about 6 to 10 bytes, which is 10 to 15% at this size. The MAC already covers integrity, so the zstd checksum (4 bytes) is redundant.
- Dictionary identity: use a 1-byte (or varint) dictionary version inside cb2's authenticated header, mapped to a pinned dictionary hash in the library, and never trust a dictID read from the compressed frame. RFC 9842's 32-byte hash costs more than half the compressed claims and only makes sense for HTTP caching. Keep old dictionaries decodable for at least the longest token lifetime, and treat the dictionary as a protocol constant shipped with every verifier in every language binding.
- A trained dictionary must be built only from public or synthetic claim shapes. If it holds real user values (emails, tenant ids) it leaks them by shipping, and it makes those values compress unusually well, which strengthens the length oracle in section 2.
- At about 200 bytes, compression time is dominated by context and dictionary setup rather than throughput. Preloading a digested dictionary (zstd CDict/DDict) per process is required. This is an inference: no measured per-call latency for 200-byte inputs was found.

### Gaps
- No primary benchmark for per-message zstd or brotli latency on 100 to 300 byte inputs with preloaded dictionaries was found. cb2 should measure its own.
- The zstd README's dictionary charts give no numeric values in text. The 2016 Facebook blog is the most recent primary numeric source found.
- Brotli's built-in static dictionary and custom-dictionary performance on tiny JSON was not quantified in sources reached.

## 5. Production precedents, and whether HPACK/QPACK makes token compression redundant

### Takeaway
Compressed signed or encrypted cookies exist in Django (signed, optional zlib), Rack (encrypted, optional deflate plus default 32-byte padding), and JWE "zip". The common large-token fix in ASP.NET Core is chunking or server-side tickets, not compression. HPACK/QPACK do not make bearer-token compression redundant: major encoders (nghttp2, and per its comment Firefox) never index `Authorization`, QPACK's dynamic table defaults to capacity 0, and HPACK only helps on repeat requests within one connection.

### Cited Findings
- Django: `signing.dumps(..., compress=True)` zlib-compresses only if smaller, flags it with a signed leading ".", and the signature is checked before inflate. Signed, not encrypted, so there is no confidentiality loss from the length. - [Django signing.py](https://github.com/django/django/blob/4.2.4/django/core/signing.py)
- Rack::Session::Cookie (rack-session): encrypted cookies via `Rack::Session::Encryptor` with `:gzip_over` deflate and `:pad_size` (default 32). The `ZipJSON` coder does `Zlib::Deflate.deflate(JSON.dump(obj))` for the unencrypted legacy path. - [rack-session cookie.rb](https://github.com/rack/rack-session/blob/main/lib/rack/session/cookie.rb), [encryptor.rb](https://github.com/rack/rack-session/blob/main/lib/rack/session/encryptor.rb)
- ASP.NET Core cookie auth splits cookies over `ChunkingCookieManager.DefaultChunkSize` 4050 characters instead of compressing. Recommended size fixes are trimming claims and server-side ticket stores (Redis, SQL). One report hit about 8 kB of chunked cookies and Safari failures. - [Microsoft Learn ChunkSize](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.authentication.cookies.chunkingcookiemanager.chunksize), [Duende blog, Apr 2026](https://duendesoftware.com/blog/20260429-aspnet-core-cookie-size-limits), [hajekj 2017 (older)](https://hajekj.net/2017/03/20/cookie-size-and-cookie-authentication-in-asp-net-core/)
- Rails 7.1 added a MessagePack cookie serializer for "smaller payload sizes" (a binary encoding, not compression). - [Saeloun blog](https://blog.saeloun.com/2023/11/15/rails-7-1-message-pack-as-message-serializer/)
- HPACK (RFC 7541 section 7.1.3): "An encoder might also choose not to index values for header fields that are considered to be highly valuable ... such as the Cookie or Authorization header fields". Never-indexed literals tell intermediaries not to index either. QPACK (RFC 9204 section 7.1.3) has the same text, and its 'N' bit forces a literal representation. - [RFC 7541](https://www.rfc-editor.org/rfc/rfc7541.html), [RFC 9204](https://www.rfc-editor.org/rfc/rfc9204.html)
- nghttp2's HPACK encoder: `indexing_mode = token == NGHTTP2_TOKEN_AUTHORIZATION || (token == NGHTTP2_TOKEN_COOKIE && nv->valuelen < 20) || (nv->flags & NGHTTP2_NV_FLAG_NO_INDEX) ? NGHTTP2_HD_NEVER_INDEXING : ...`, with the source comment that this is "the same criteria used in Firefox codebase". - [nghttp2 lib/nghttp2_hd.c](https://github.com/nghttp2/nghttp2/blob/master/lib/nghttp2_hd.c)
- Go's `golang.org/x/net/http2/hpack` exposes `HeaderField.Sensitive` ("this header field should never be indexed"), and sensitive fields are not added to the dynamic table. - [Go hpack.go](https://github.com/golang/net/blob/master/http2/hpack/hpack.go), [encode.go](https://github.com/golang/net/blob/master/http2/hpack/encode.go)
- QPACK `SETTINGS_QPACK_MAX_TABLE_CAPACITY` "default value is zero", so no dynamic-table compression happens unless the decoder advertises capacity. - [RFC 9204 section 5](https://www.rfc-editor.org/rfc/rfc9204.html#section-5)
- Cloudflare called HPACK "the silent killer feature of HTTP/2" for removing repeated headers. - [Cloudflare blog (older)](https://blog.cloudflare.com/hpack-the-silent-killer-feature-of-http-2)

### Inferences
- A bearer token in `Authorization` through nghttp2- or Firefox-style encoders is sent as a full literal on every request. At most static Huffman coding applies, which for base64url text saves roughly a quarter since most of those symbols get 6-bit codes (inference from the HPACK Huffman table, not measured). Payload compression in the token is not redundant with HPACK for Authorization headers.
- A token carried in a cookie of 20 bytes or more is indexed by nghttp2, so repeats on the same connection collapse to a 1 to 2 byte index. On that path HPACK makes in-token compression mostly redundant for wire bytes, but not for the 4 KB per-cookie limit, server header-size limits, storage, logs, or the first request per connection.
- Size perspective for cb2.public: an ML-DSA-65 signature is 3309 bytes and Ed25519 adds 64 ([FIPS 204](https://csrc.nist.gov/pubs/fips/204/final)), so shrinking claims from 217 to 62 bytes saves about 155 bytes of about 3.6 KB raw (about 4%, before base64url). For cb2.local (24-byte XChaCha20 nonce plus BLAKE3 tag plus claims) claims dominate, and compression with fixed padding is a large relative win, for example roughly 290 to 107 base64url characters for the claims part.
- Recommended shape for cb2, from the sources above: (1) cb2.public: optional dictionary compression is safe with respect to confidentiality. Sign the compressed bytes and verify before bounded inflate. (2) cb2.local: dictionary compression only with mandatory padding to a fixed size class, a format flag and dictionary version inside the authenticated header, MAC verification before decrypt and inflate, and a hard output cap. Offer a "no compression" mode for issuers that put attacker-influenced and secret claims in one token and cannot accept the residual size-class leak.

### Gaps
- Whether Chrome's and Go's HTTP/2 client stacks mark `Authorization` as never-indexed was not confirmed. Only nghttp2 (and the Firefox claim in its comment) was verified in source.
- Shopify, Cloudflare, and Google production use of compressed auth tokens or cookies was not found in any source. No public precedent was located beyond the frameworks above.
- No source found on gRPC metadata compression treatment of `authorization` beyond the general HPACK behavior, since gRPC over HTTP/2 inherits the transport's encoder policy.
- Whether Rails' encrypted cookie jar (ActiveSupport::MessageEncryptor) compresses was not confirmed. The sources found only show serializer changes.
